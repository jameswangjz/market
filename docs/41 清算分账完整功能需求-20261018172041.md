# 清算分账完整功能需求

版本：实施需求 V2。生成时间：2026-10-18 17:20:41，北京时间。以本轮已确认口径作为开发依据；现状差异不代表已实现。

本需求整合已确认的利润清算、月度批次、双方调整提案、普通退款、版本升降级及本轮成本回收和分角色报表要求。目标是让订单、成本、利润分成、退款冲回、应收应付和报表可以逐笔核对。本文描述完整目标功能，用户已授权按最新需求设计、开发和验证；已确认口径与未完成开发必须分别跟踪。

## 1 业务范围与基本原则

REQ-001 清算对象包括已支付的购买与续费订单、已完成的普通退款、已经生效并正式入账的版本升降级正负调整，以及经批准的补差调整。订单未支付不进入清算；普通售后工单存在与否不影响清算。

REQ-002 买方是资金支付和退款接收方，不是利润分成方。利润分成方固定为平台运营方、数据或服务提供方、数据服务方、专家、渠道五类。每类可以关联多个真实收益主体，不能只记录“专家”“渠道”等通用名称而不区分实际对象。

REQ-003 只有提供方定义供货成本，全部供货成本应付给该订单对应的提供方；其他各方不另外登记成本，其收益通过利润分成体现。提供方成本与提供方利润分成必须分项核算。退款时供货成本默认按退款金额比例冲回，适用于所有交付方式，不仅限于SaaS或API；不可返还成本可作为有依据、经批准的例外处理，不得由系统自动推定。

REQ-004 按订单或经济段计算，再汇总为批次、月份、提供方、产品、收益主体及年度视图。汇总表不得另用不同公式计算，不得以列表分页或固定条数限制作为统计范围。

REQ-005 业务清算不等同于法定财务报表、税务申报或真实银行支付。尚未接入真实支付、银行对账和财务系统时，必须明确标识人工登记或模拟结果，不得显示为已取得银行回执。

## 2 金额定义与守恒

| 名称 | 定义 |
| --- | --- |
| 原始实收金额 | 已确认支付记录对应的真实或明确标注的模拟收款金额，不因清算提案而被改写 |
| 清算收入金额 | 按冻结经济记录计入本期清算的正向金额；与原始实收不同的部分须有独立、可审计的补差依据 |
| 供货成本 | 提供方对应版本、购买数量或订阅月数的成本快照 |
| 可分配利润 | 清算收入金额减供货成本；正负调整分别列示，不混淆现金退款与利润冲回 |
| 各方利润分成 | 可分配利润依冻结或最终确认的分成比例分配给五类参与方的金额 |
| 提供方应收 | 应回收供货成本加提供方利润分成，再考虑其退款冲回和其他已批准调整 |
| 平台分成收益 | 五方利润分成中归属于平台的部分，不等于全部可分配利润，也不直接等于会计净利润 |
| 本期净清算额 | 正向清算收入加所有归属本期的收入正负调整；必须能够解释与成本和五方分成的关系 |

REQ-006 正向标准订单遵循以下公式：

```text
订单收入 = 版本单价 × 购买数量或订阅月数
供货成本 = 版本单位成本 × 相同购买数量或订阅月数
可分配利润 = 订单收入 − 供货成本
五方利润分成合计 = 可分配利润
订单收入 = 提供方成本回收 + 五方利润分成合计
```

文件和线下服务按一次性购买口径计算；API、模型API交付及SaaS按已确认的月付和经济段规则计算。线下报价调整后的成本、价格使用审核后订单快照。

REQ-007 新登记和新订单禁止售价低于成本。历史异常、退款、差价和调整可以形成负向经济记录，不得将负利润强行归零后丢失损失。亏损承担政策如果超出既有同比例冲回范围，须另行确认。

REQ-008 分成比例合计须为100%。一类存在多个收益主体时，该类内部比例或确定金额还须合计等于该类金额。全链使用十进制金额，以分为最小记账单位；统一尾差分摊算法，保证明细、汇总、退款和导出金额一致，不能把未配置的大额比例差异当作尾差自动归给提供方。

REQ-009 示例：订单150元、成本100元，平台20%、提供方80%、其他为0。平台利润分成10元，提供方利润分成40元，提供方成本回收100元；提供方合计应收140元。100元成本不能算成平台利润，也不能漏记为无人应收的余额。

## 3 收益主体与成本回收台账

REQ-010 登记产品或配置清算规则时，为非零分成指定实际收益主体，保存主体类型、主体ID、名称、所属企业、分成类别、收款配置引用及生效版本。专家、渠道、数据服务方均可配置多个主体。零分成允许不配置收款主体；非零分成但主体缺失时，允许试算并列明缺项，但不得确认付款。

REQ-011 一个实际主体可以承担多个分成类别，报表须同时支持按类别查看和按主体合并；不得把同名主体自动认定为同一收款人。

REQ-012 每张正向清算单分别产生全部供货成本向提供方应付，以及五类利润分成应付。成本不得留归平台或分摊给其他收益主体。平台自身分成记为内部收益归属，不当作必须向自身银行账户再打款的外部债务。

REQ-013 成本台账至少记录：订单、产品版本、原成本快照、最终确认成本、成本应付主体、确认金额、已支付金额、未支付金额、已冲回金额、实际追回金额、已抵扣金额及关联凭证。

REQ-014 已确认采用提供方成本和利润分成合并付款、分项记账、分项冲回、分项展示的方式。合并付款凭证必须能够追溯到成本及利润分成各自的金额。

## 4 冻结规则与最终确认基线

REQ-015 新订单冻结产品版本、单价、单位成本、总成本、购买时长、币种、五方比例、各收益主体及规则版本。后续产品编辑、规则切换和参与方变更不追溯修改已冻结记录。

REQ-016 清算调整提案由平台方或原提供方提出，必须由对方确认，禁止同一方自提自批。提案保留原值、新值、说明、操作者、确认人及时间。

REQ-017 双方确认并锁定后形成不可变的最终清算基线，包含清算收入、供货成本、利润、各方比例和金额、成本归属、主体身份及确认版本。无调整时，原计算结果经锁定成为最终基线。

REQ-018 退款冲回使用原订单相应经济段最终确认的清算基线，而不是退款时产品的现行规则，也不是已经被双方调整结果替代的原订单比例。基线确认、退款冻结、冲回累计和付款须有并发控制，防止使用过时版本。

REQ-019 清算提案不能修改买方支付事实和退款上限。调整清算收入与原实收不一致时，必须明确补差来源及承担主体，如补收、扣减、平台承担或其他获批调整；不得凭空增加可支付资金。补差类别与凭证字段在详细设计中落实，不改变本项已确认原则。

REQ-020 已确认、已付款和已归档结果不得直接编辑。后续变化使用关联原记录的补充调整单，在获准的开放期间处理，保留完整历史版本。

## 5 月度清算范围与手动生成

REQ-021 统一采用北京时间自然月，区间为月初00:00含起点至下月月初00:00不含终点。时间字段以时区明确的时间保存，不依赖浏览器或服务器本地时区。

REQ-022 正向订单按支付确认时间归属月份；不因其后进入退款处理中或已退款而遗漏原正向支付事实。退款按完成时间归属月份，版本升降级调整按其正式入账时间归属月份。支付补款与升降级经济调整不得重复计入利润。

REQ-023 由具备权限的平台人员手动选择月份并生成清算批次、成本及分成明细和报表预览。不设置每月1日01:00或其他时间自动生成上月草稿的任务，也不自动批准或付款。手动生成及重试须幂等、提供明确失败信息；同月已有有效批次时须遵守既有重算和确认限制，不得静默覆盖。

REQ-024 只统计目标期间的有效经济事实。提供方是否完成交付、是否存在售后工单，不作为额外剔除条件；未完成退款申请不提前计为已完成退款。

REQ-025 同期已支付并完成退款的订单保留一条正向事实及相应负向事实，报表展示收入、退款和净额；不得删除正向记录或同时净额扣减、负向冲回导致重复扣减。

REQ-026 跨月退款计入退款完成月，并追溯原订单、原清算单、原批次和最终基线，不重写已经确认的历史月份。尚未确认的期间可以按重算规则重新生成。迟到记录和补录凭证须保留业务发生时间与入账期间，不得默默丢失。

## 6 清算批次和清算单状态

REQ-027 批次沿用既有核心状态，不恢复批次级的disputed、exception、recon_exception：

```text
已生成 generated → 待确认 pending_confirm → 已确认 confirmed → 已付款 paid
未进入确认及后续阶段的有效批次，可经显式重算变为已作废 superseded
未确认批次可按授权进入已回滚 rolled_back，再由明确操作重算
```

需要实际分笔付款时，付款处理中的详细进度独立记录；只有确有部分付款事实时，才展示部分付款，不能仅靠预留状态宣称已支持真实资金执行。

REQ-028 清算单沿用待确认pending、调整异议disputed、已调整adjusted、提案被拒绝proposal_rejected、已锁定locked、已付款paid、已作废superseded。提案被拒绝后可以继续提交提案；对最新有效提案仍未达成一致的清算单不得直接锁定。

REQ-029 所有有效清算单锁定后批次进入待确认；平台批次确认后进入已确认，关联清算单保持锁定。批次确认不是替代原提供方的提案确认。

REQ-030 已确认及后续阶段批次禁止重建；存在任何实际付款、回收或不可逆外部凭证时，即使显示状态异常也禁止重建。未确认批次重算须作废旧批次及关联有效清算明细，保留原因和审计。若旧基线已经被退款或升降级引用，禁止静默作废，须按关联调整策略处理。

REQ-031 正向清算记录可保留“已付款”兼容状态，但须由实际付款或明确的模拟登记支撑；负向记录使用独立的回收或抵扣状态，不再仅用“已付款”表达已经追回。

REQ-032 批次清算完成、正向付款完成、负向回收完成是三个不同判断。已确认：负向未回收时分别展示清算确认、付款和回收进度，可以展示“正向付款完成、仍有待追回”；仅当所有应付应收完成清结，才称“资金已结清”。这项结清判断不替代或混淆批次既有主状态。

## 7 退款冲回与应追回

REQ-033 买方退款沿用已确认权限：买方企业超级管理员或管理员申请；平台系统管理员、平台运营人员审核及确认执行；财务人员保留人工到账确认，但不恢复已被替代的普通退款审批权限。版本降级继续走既有自动差价流程，不混入普通退款审批。

REQ-034 买方退款完成后，形成关联原订单的负向清算事实。其内容分别包括收入冲回、供货成本冲回、五方利润分成冲回，不把退款全额视为负利润。

REQ-035 普通未跨版本订单按最终基线计算累计冲回，本次冲回等于累计应冲回减此前已确认冲回，避免多次小额退款的重复扣减、超额冲回和分币尾差。默认供货成本按退款金额占对应成交金额的比例冲回：无例外时，全额退款冲回全部成本，部分退款同比例冲回。不可返还成本例外须记录证据、核定金额、承担主体、批准人和时间，并形成明确的成本及利润冲回计划；不得默认为已经回收，累计冲回不得超过原确认成本。跨版本场景按对应经济段分别计算，不使用全订单单一比例覆盖所有经济段。

```text
累计成本冲回 = 最终确认的该段供货成本 × 该段累计退款金额 ÷ 该段对应成交金额
本次成本冲回 = 本次累计成本冲回 − 此前累计已确认成本冲回
```

上式适用于无已批准成本例外的默认情形；存在例外时按批准的冲回计划执行，并单列例外对利润和各方金额的影响。成本冲回比例不等于买方退款金额的确定算法。SaaS按已用时长、有限额度API按用量、不限额度API按时长、文件及线下服务按适用审批规则先确定退款金额，再计算成本冲回。清算收入存在补差时，还须满足REQ-019的实收和差额来源约束。

REQ-036 跨版本订单按各经济段最终基线分别处理；切换前已消费部分不追溯，未使用剩余和未来续费段分别计算。普通退款资金来源继续优先退最近升级补款，清算冲回归属不按支付资金先后次序重分配。

REQ-037 原清算尚未锁定、最终基线尚不存在时，可以先生成明确标注的冲回试算，不因此阻塞已获批的买方退款。清算冲回状态独立跟踪，原基线确认后再确认冲回结果；未确认基线的清算结果不得付款或宣称资金已结清。

| 回收术语 | 含义 |
| --- | --- |
| 应冲减未付款 | 该参与方尚未收到对应资金，先减少其未付应付，不产生虚构的现金追款 |
| 应追回 | 对应资金已经支付给该参与方，退款或调整后其应返还、抵扣的债务金额 |
| 已追回 | 已取得有效回款依据并核验到账的金额，不含只有计算结果或待执行的抵扣 |
| 已抵扣 | 已经与同主体、同币种、具备依据的有效应付款完成核销的金额 |
| 待追回余额 | 已确认应追回减已追回、已完成抵扣及其他获批核销金额；未执行的未来计划不减少余额 |

REQ-038 应追回不仅包含利润分成；如果供货成本已经付给提供方，还包括按退款比例应冲回的该部分成本。平台自身利润冲回作为内部收益冲减，不伪造外部回款。

REQ-039 部分已付款时，按可追溯的付款分配记录区分未付款冲减和已付款追回，不能把同一退款既抵减未付余额又全额追款。

REQ-040 回收支持人工回款登记和审批、后续应付款抵扣、明确授权的其他核销。跨主体、跨币种不得自动抵扣；已用于其他付款、退款或抵扣的额度不能重复占用。减免、坏账和核销如果需要，应单独审批，不当作已追回。

REQ-041 买方退款与参与方资金追回为独立状态链。已确认不把参与方是否返还资金当作已获批买方退款完成的前提；平台垫资和风险余额必须单列，清算冲回及实际回收分别跟踪。

回收示例：按REQ-009的150元订单，如退款75元并继续采用同比例成本冲回，则收入冲回75元、成本冲回50元、利润冲回25元，其中平台分成冲回5元、提供方利润分成冲回20元。如果提供方已经收到140元，对提供方应追回70元，包含50元成本和20元利润；平台自身5元作为内部收益冲减。如果提供方尚未收款，则减少其70元未付应付，不记为已经追回70元现金。买方收到75元退款的凭证与提供方返还70元的凭证分别记录。

REQ-042 退款后权益沿用现行规则：有限额度API按比例扣减额度，SaaS及不限额度API扣减未使用尾部时段，文件退款停止该订单后续下载。资金回执、资源执行和清算调整均需关联，不因新增回收台账而破坏现有Saga及幂等机制。

## 8 版本升降级与清算

REQ-043 版本变更沿用“原版本剩余部分冲回＋目标版本剩余部分重新计入”。同时冲回或计入收入、供货成本和五方利润分成，不能仅将净补款作为完整目标版本订单，再扣一次完整成本。

REQ-044 原版本采用原经济段最终确认的清算基线，目标版本采用本次确认冻结的目标规则。资金补差使用差额，清算仍保留独立正负经济记录；旧基线被正式调整后，其未使用部分冲回也须使用调整后的基线。

REQ-045 当前剩余和已经购买的未来续费分别计算；API与SaaS多订单关系、未来时段不提前重置额度、相同版本续期不叠加当期额度等权益规则保持不变。

REQ-046 普通退款、版本降级退款、原版本冲回和目标版本重计必须有明确类型、关联ID和排重规则，禁止一笔降级退款同时被普通退款适配器再次冲回。

## 9 付款和资金台账

REQ-047 应付按收益主体、币种、批次归集，明细能够回到成本行、利润分成行、订单和经济段。付款安排必须保留原应付分配，不得只记录批次总额。

REQ-048 每笔付款或回款记录包含：内部单号、方向、主体、币种、金额、支付渠道或人工方式、业务凭证、操作人、复核人、发生及确认时间、状态、失败原因和关联应付或应收分配。

REQ-049 区分计算确认、付款处理中、部分成功、成功、失败和撤销。重试不得重复打款；人工修改状态不应替代明确的付款、回款或模拟依据。

REQ-050 未接银行时，保留模拟支付和人工确认能力，页面、导出和报告标识“模拟确认”或“人工登记”。不在本轮承诺真实银行到账、扣款、自动追款、财务总账或税务申报已实现。

REQ-051 抵扣以独立凭证记录，分别减少应收和应付，保留抵扣前后余额及审批依据。负向行不能简单生成SIM-PAY号并标为已付款后消除追回余额。

REQ-052 权限沿用平台系统管理员、平台运营、财务清算的现有清算操作授权；普通退款审批继续遵循REQ-033。高风险资金动作建议引入不同操作者复核，具体分权在详细设计前明确，不由报表查看权限自动赋予执行权限。

REQ-056 实收、实际退款等现金指标来自支付和退款凭证；收入、成本、利润来自清算经济记录。两者分别展示并提供差异桥接，不把升降级资金差额与其正负清算腿重复累加。

REQ-059 贡献排名包括：订单收入排名、可分配利润排名、提供方利润分成排名，以及各提供方对平台、数据服务方、专家、渠道分成的贡献排名。允许切换发生额或冲回后净额，默认采用净额并显示口径；成本回收不混入利润分成排名。

REQ-060 产品汇总支持按产品、版本、提供方、月份统计数量、收入、退款、成本、利润、五方分成、成本回收和应收应付，并下钻到同口径订单明细。

## 13 年度汇总与归档

REQ-069 提供年度动态视图，按同口径月份聚合，可随时浏览和下载。建议次年1月在12月清算生成后产生年度汇总草稿，不将其自动认定为财务年报最终版。

REQ-070 年度业务报告至少包括12个月汇总、收入和退款数量、成本、利润、各方分成、提供方及产品贡献排名、应付应收余额桥接、跨期退款和调整、未解决事项、数据截止时间和报告版本。

REQ-071 正式年度清算报告经授权复核后形成快照，保存查询范围、包含的有效批次和明细版本、生成与确认时间、复核人、文件校验信息及报告状态。年度归档不自动代表完成会计结账或税务申报，不固定要求在2月或3月完成。

REQ-072 归档后新增跨期退款、调整和凭证通过后续调整报告或新版本补充说明体现，原归档文件不被覆盖。新年度期初余额承接上一年度尚未结清的应付和应收，不把年度跨越当作欠款清零。

## 14 检索与导出

REQ-073 平台和提供方支持在线浏览与下载总体、月份、产品、主体、订单、退款冲回、资金及年度报表；导出沿用当前筛选和授权，但覆盖筛选范围全部数据，不只是当前页。

REQ-074 字段中文显示，ID使用BATCH、SET、ORD等业务编号；内部主键不作为主要展示内容。真实收益主体须明确显示名称，不能删除内部关联关系以隐藏ID。

REQ-075 页面同时显示统计数据截止时间、期间、币种、数量定义、状态过滤和是否包含未确认记录。超过同步导出能力时生成异步导出任务，提供进度、失败重试和受控下载，不静默截断2000条。

REQ-076 汇总和导出使用统一十进制聚合与舍入；多币种不直接相加，未明确换算规则时分币种展示。是否新增XLSX或PDF正式报告，在详细设计中按模板需求确定，不影响保留CSV完整数据导出。

## 15 审计与数据安全

REQ-077 规则登记变更、主体映射、清算生成重算、提案及确认拒绝、锁定、批次确认、退款冲回、付款、回款、抵扣、核销、导出及归档全部可审计。

REQ-078 审计记录包含操作者及作用域、操作时间、对象编号、前后状态和数值、原因、请求及幂等标识、关联经济段和规则版本、结果和凭证引用。失败动作保留适当操作证据，但不得部分提交财务结果。

REQ-079 服务端实施企业及主体隔离，列表、明细、汇总、排名、导出和文件下载一致授权；敏感收款信息脱敏并独立授权。已确认基线和资金凭证不得直接物理删除。

REQ-080 同一月份生成、同一基线退款累计、同一主体应付余额和抵扣占用必须有事务级一致性与幂等保护。Redis重启或事件缺口不得以重置计量水位、重复扣额或重复冲回掩盖问题。

## 19 确认后的实施顺序建议

先完成最终基线与成本加分成的金额模型、真实收益主体及权限，再开发退款衔接和应收应付及回收抵扣。随后补齐平台与提供方报表、多主体报表、全量聚合和导出，最后完善手动月度批次及年度快照归档；不开发月度自动生成。

每组先做范围内的金额、权限、并发和回滚测试；多个相关功能具备条件后再统一执行交易、退款、清算和报表组合回归，不为每个界面小改动重复跑全量测试。真实银行支付、银行追款及财务总账联调单列后续任务，不影响首期模拟和人工登记验证。

| 交付方式 | 当前退款成本冲回覆盖 | 当前边界 |
| --- | --- | --- |
| SaaS租户或权限开通 | 普通退款经济计划及负向清算支持按比例冲回成本 | 最终提案调整结果与退款基线的统一衔接仍待改造 |
| API及模型API交付 | 支持成本比例冲回，跨版本使用经济段处理 | 买方退款金额按有限额度用量或不限额度时长确定，不等于成本冲回算法 |
| 文件下载 | 已支持；人工核定退款金额后，以文件退款经济计划计算比例成本冲回，并停止本订单后续下载 | 要求完整的新订单经济快照和可校验的退款历史，不能把任意历史人工核定单当成自动执行依据 |
| 线下培训、咨询、定制开发 | 尚无与上述线上交付等价的完整受控自动执行链路 | 通用负向清算函数存在比例计算代码，但不能据此宣称线下退款的审批、执行、成本冲回、回收与报表全链路已经具备；按本需求统一补齐 |

主要实现入口：`backend/app/refund_settlement.py`、`refund_planning.py`、`refund_file_resources.py`、`refund_execution.py`；通用兼容入口为`main.py`中的`create_refund_negative_settlement`。其中普通退款目前主要依经济计划冻结规则，尚不能等同于本需求要求的所有最终确认清算结果冲回。
