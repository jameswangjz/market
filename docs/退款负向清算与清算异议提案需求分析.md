# 退款负向清算与清算异议提案需求分析

## 1. 需求结论

本次需求与“按自然月清算”的模型一致，不存在必须保留批次级 `disputed`、`exception`、`recon_exception` 的冲突。原始已支付订单形成正向清算单；退款完成后形成与退款单、原订单关联的负向清算单，负向清算单在退款完成日期所属月份进入月度批次。

售后状态与清算状态解耦。售后过程不改变原始支付订单的清算资格，退款结果通过独立的负向清算单反映，因此同一订单可以在清算报表中同时出现正向订单清算和退款负向调整。

## 2. 月度取数规则

1. 正向范围：支付单存在 `paid_at`，支付确认日期位于指定自然月，支付状态为已支付、退款中或已退款的订单。
2. 退款范围：退款单状态为已完成，`completed_at` 位于指定自然月的退款负向清算单。
3. 正向订单按完整已支付金额、订单版本成本和有效清算规则计算；退款金额不在正向清算单中重复扣减。
4. 退款负向清算按原清算单金额、成本、利润及五方分成比例按退款金额比例冲回；没有原清算单时按订单版本成本和产品规则计算。
5. 售后状态不作为正向订单的排除条件，售后退款通过负向清算处理。

## 3. 状态模型调整

清算批次保留生成、待确认、已确认、付款中、部分付款、已付款、作废等业务状态，不再产生批次级 `disputed`、`exception`、`recon_exception`。对账差异记录在对账表中，并在差异未关闭时阻止付款，不污染批次状态。

异议下沉到清算单：清算单提交调整提案后变为 `disputed`，另一名清算操作人员确认或拒绝提案。确认后更新金额和五方分成，拒绝后恢复为待调整状态。所有提交、确认、拒绝、金额变化均写入前后值审计日志。

## 4. 已实现与验证

- `payments.paid_at` 已增加，历史开发数据启动时按支付记录时间回填。
- `settlements` 已增加 `refund_id`、`reference_settlement_id`、`is_refund`。
- 退款完成自动生成幂等负向清算单。
- 月度批次按支付确认时间和退款完成时间取数。
- 批次异常状态赋值、批次异议按钮和对账异常污染已移除。
- 新增调整提案提交、查询、确认、拒绝接口及前端操作入口。
- 已通过后端语法检查、前端生产构建，并部署到 `market` 命名空间；健康检查、登录、清算批次和清算单查询已验证。

## 5. 验收场景

支付确认日期在目标月的订单应生成正向清算单；退款完成日期在目标月的订单应额外生成负向清算单；退款完成在其他月份时不进入当前月；售后处理中但没有退款的订单仍可清算；批次对账差异只阻止付款；清算单调整进入提案状态，提交人不能本人确认，其他清算操作人员可确认或拒绝。
