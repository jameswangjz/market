# 清算财务边界确认与增量部署设计

## 1. 已确认范围

承接48号阶段报告，三项边界均已收到用户明确确认。本文描述增量契约，不表示已经完成运行环境验证；部署结果另附实际版本和证据。

1. 多经济段成本例外逐段填写保留金额、证据，由对侧一次审批整张提案。
2. 外部补差采用人工凭证登记和独立复核，明确不代表银行自动对账。
3. 补差后按退款金额占买方实付金额的比例冲回最终清算及平台承担记录；额外差额仅为内部调整，买方累计退款不得超过实际实付。

## 2. 多经济段成本例外

每段绑定经济段、来源清算单、最终基线摘要、正常冲回依据、保留成本和证据。整张提案采用同一个明确承担主体，不能按第一段代替其他来源，不能隐式平均分配。

每段正常退款金额、成本和利润均以负数表示。保留成本为R时，实际成本等于正常负成本加R，实际利润等于退款负金额减实际成本；承担主体的分成再减少R。独立损失单列，不与正常分成累计预算混淆。买方已完成退款及资源回收证明不变。

提交及审批均重新验证来源摘要和上限，按固定顺序锁定来源；单段和多段已批准保留成本共用累计预算。必须由对侧独立审批，拒绝自审及同侧审批。任何段校验失败，整张提案及应用回滚。已入账的退款不能通过更新提案静默重写，须显式调整。

## 3. 人工补款凭证

流程为补差提案、独立审批、登记到账凭证、不同人员复核、核验覆盖。保存金额、币种、日期、流水参考、证据、说明和操作人；凭证不可覆盖，重复请求必须幂等且拒绝不同载荷复用。

复核方法明确为人工独立复核，银行自动核验标记保持false。金额必须对应实际补差缺口，不新增或改写买方支付记录，不增加买方退款上限。未经复核、被拒绝、来源摘要变更或重复流水不能解除资金门禁。

## 4. 补差后退款

例如买方实付150元，最终清算160元，平台利润承担10元，退款30元时比例为20%；买方只退30元，最终清算按比例冲回32元，平台承担记录相应冲回2元。32元与30元的差额属于内部清算，不是额外向买方付款。

每笔保存实际支付来源、退款完成证明、最终基线及补差证明摘要。累计计算后取本次增量，保证分币舍入可追溯、最后一笔关闭余额。并发和重试不得重复占用来源预算或重复形成资金行。

多来源只接受精确绑定；缺失证明时财务暂挂，不撤销或阻塞已经获批并完成的买方退款。成本例外、跨订单或其他组合若尚无完整守恒接线，应明确拒绝自动入账，不静默使用原始订单规则。

## 5. 验证与部署门禁

- 先运行三项新增模块的专项测试，再运行相关退款、成本、资金及报表组合，不重跑无关平台全量测试。
- 验证原单先生成后审批、部分退款再全退、重复凭证、自审、跨企业、并发额度和中途失败回滚。
- PostgreSQL使用独立临时数据库，不修改开发环境历史清算事实。
- 发布只使用明确提交的可信构建，标签为YYYYMMDDHHMMSS-GitSha。部署前备份，部署后核对API、Web、相关Worker和CronJob版本。
- 部署后核对受保护订单及依赖指纹、权限拒绝、关键接口和浏览器展示；不修改历史计费游标，不推定缺口为零。
- 完成实现与验证后转待验收，用户前端验收后才能视为业务接受。真实银行支付和自动对账不在本次模拟验证结论内。
