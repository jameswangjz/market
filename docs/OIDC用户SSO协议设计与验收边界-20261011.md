## 2. 两条认证链路必须独立

| 维度 | 机器 OAuth client_credentials | 人员 OIDC 授权码 + PKCE |
| --- | --- | --- |
| 主体 | 后端服务/客户端，不代表登录用户 | 平台已认证且获应用授权的用户 |
| 用途 | 平台调用第三方 OPEN、RENEW、CHANGE、USER_ASSIGN 等管理接口 | 第三方 SaaS 确认人员身份并建立自己的会话 |
| 实际端点 | `/oauth/token`、`/oauth/introspect` | `/oidc/authorize`、`/oidc/token`、`/oidc/userinfo`、发现/JWKS |
| 客户端 | 现有机器客户端 | 独立 OIDC 客户端、独立密钥与生命周期 |
| 作用域/受众 | 现有机器资源域，如 `market-resource` 和管理 Scope | `openid` 和实现支持的人员 Scope；ID Token 受众为 OIDC client_id |
| 返回 | 机器 access_token；不建立用户身份 | RS256 ID Token + 随机 opaque 人员 access_token；各有验证及用途边界 |
| 权限依据 | 管理接口允许的产品/操作范围 | 用户、实际企业成员关系、应用授权、订阅和租户映射 |
| 浏览器持有密钥 | 禁止 | 同样禁止；本批 form client_secret 表示机密后端客户端，并非纯 SPA 公共客户端 |

产品 ID、订阅 ID、外部租户 ID 和 OAuth/OIDC client_id 是不同标识。不得复用机器 client_secret 来换人员 token；不得把平台控制台 Bearer、人员 ID Token 或人员 access_token 当成机器管理令牌。即使签名库共用，验证器也必须明确区分 issuer、audience、token 用途和客户端类型。

`client_credentials` 是服务身份授权，不是用户 SSO。[OAuth 2.0 RFC 6749](https://www.rfc-editor.org/rfc/rfc6749#section-4.4)

## 3. 实际协议接口与互操作限制

| 接口 | 实际调用/返回边界 | 验收边界 |
| --- | --- | --- |
| `GET /.well-known/openid-configuration` | 匿名发现；公开 issuer 与端点、算法和支持能力 | 与实际公开 URL 一致；不宣告未实现的 grant、认证方式或会话能力 |
| `GET /oidc/jwks` | 匿名发布 RS256 验签公钥及 kid | 不含 RSA 私钥参数；跨副本/重启一致 |
| `POST /oidc/authorize` | 平台 Bearer + JSON OAuth 参数及 enterprise_id；成功返回 JSON `redirect_url` | 这是已登录平台用户的授权 API，不是浏览器 session 登录端点 |
| `POST /oidc/token` | form 授权码、客户端认证及 PKCE verifier | 严格绑定 client/redirect/PKCE；仅支持实现声明的 grant |
| `GET /oidc/userinfo` | 人员 access_token | 重新核查用户/企业/租户/应用授权；ID Token 和机器 token 不可替代 |
| `POST /api/products/{id}/oidc-client` | 无请求体；首次创建独立 client，后续返回既有 client 元数据 | 仅首次返回 secret；读取产品既有回调白名单，无 GET/PUT 或白名单更新能力 |

`POST /oidc/authorize` 接受 JSON：`response_type` 默认且仅支持 `code`；必填 `client_id`、`redirect_uri`、`enterprise_id`、`state`、`nonce`、`code_challenge`；`scope` 默认 `openid`，必须含 `openid` 且只能使用 `openid profile email`；`code_challenge_method` 默认且只接受 `S256`。state/nonce 长度为 16–255，challenge 为 43 位 base64url 字符。额外 JSON 字段被拒绝。订阅由后端按企业/产品组合解析，不接受调用方指定 tenant_id 或 subscription_id 覆盖绑定。

`POST /oidc/token` 只接受 `application/x-www-form-urlencoded`，参数为 `grant_type=authorization_code`、`code`、与授权时相同的 `redirect_uri`、`code_verifier`，以及客户端认证。支持 `client_secret_basic`（Authorization Basic）和 `client_secret_post`（form client_id/client_secret），发现元数据同步声明两者。请求最多 16384 字节、20 个 form 字段，重复参数或值超过 4096 字符拒绝；不接收 JSON 或 query 替代 form。

成功兑换返回 `token_type=Bearer`、`access_token`、`expires_in=300`、`scope` 和 `id_token`。code 有效期 120 秒；ID Token 和 opaque access_token 有效期各为 300 秒，协议期限使用服务端 `time.time()`，不接受客户端 supplied time。人员 access_token 是 48 字节随机源生成的 URL-safe opaque 值，仅摘要落库，不能用 JWKS 验签它；userinfo 通过摘要查找当前授权记录。ID Token 使用 RS256，含 Authlib 生成的 iss/aud/iat/exp/nonce/auth_time 等协议 claims，aud 为独立 OIDC client_id。

业务身份字段为 public `sub=user.id`、`enterprise_id`、`tenant_id=subscription.external_tenant_id`、`subscription_id`；profile scope 增加 name，email scope 增加 email 和真实 email_verified。当前没有外部用户 ID、app_id 或 product_id 的自定义 claim，不应凭空扩充。授权、兑换、userinfo 和 client 配置响应使用 no-store/no-cache。不支持 refresh_token、隐式流、动态注册、登出、离线访问或独立撤销端点。

### 3.1 auth_time 与旧控制台会话

`main.py::issue_token` 为新控制台 HS256 JWT 写入 iat。authorize 从已经通过 current_user 认证的同一 Bearer 读取整数 iat，作为 code.auth_time，随后由 OpenIDCode 放入 ID Token；它不是授权签发时刻，也不是客户端请求字段。缺少 iat、类型不是整数或超过服务器当前时间 60 秒的会话返回 401，要求重新登录。旧无 iat 的控制台 JWT 可能仍可调用原业务接口，但不能用于新 OIDC 授权，不能将重登提示误报为 PKCE/租户故障。

### 3.2 POST 授权 API 不等于标准浏览器 SSO

标准 RP 通常通过浏览器导航授权端点，由 OP 登录/会话机制识别用户。本批实际只有 POST API，要求调用方先具备平台 Bearer并返回 JSON `redirect_url`；没有 GET 浏览器授权桥接、平台 cookie/session 登录或直接 302 的完整链路。内部 Authlib GET/302 适配不改变对外 HTTP 契约。

第三方浏览器不能凭一次 URL 导航自动附带平台 Authorization header。不得通过 query、跳转 URL、第三方页面或浏览器存储搬运平台 Bearer 来弥补这项缺口；不得为迎合通用 RP 宣称该端点已满足浏览器授权互操作。

后续需明确可信平台前端发起授权与第三方 RP 登录请求之间的事务桥接，或实现标准浏览器授权入口及安全平台 session。桥接须绑定原始 RP 登录事务，不能接受任意未绑定的 state/nonce/PKCE 请求。未完成前，只能验收“平台 Bearer 授权 API + 代码兑换”，不能称“完整用户 SSO 已验收”。标准授权码身份认证与 ID Token 验证边界见 [OIDC Core](https://openid.net/specs/openid-connect-core-1_0.html#CodeFlowAuth)。

## 4. 客户端与回调配置

人员客户端归属单个 SaaS 产品，使用独立表和 `oidc_` 前缀 client_id；product_id 和 client_id 各有唯一约束。创建接口只接受 `saas` + `tenant_access`，产品状态须为 published 或 pending_integration；调用者须已实名、已激活，并为提供方企业实际管理员，或明确允许的平台 super_admin/platform_operator。其他平台角色拒绝。配置管理权限不等于人员登录权限，所有平台角色在人员 eligible 检查中被拒绝。

现有回调登记规则：最多 20 个，每项不超过 2000 字符，去重；须完整 URL、有主机和 `/` 路径；禁止空白、控制字符、反斜杠、URL 用户名/密码、fragment、通配符和无效/零端口。一般须 HTTPS，仅明确允许 `localhost`、`127.0.0.1`、`market-mock-saas` 使用 HTTP。后者是隔离模拟例外，不是生产 HTTP 白名单。

实际 OIDC client 每次查询从 `Product.oidc_redirect_uris_json` 读取白名单，不另存独立 allowlist；provision 接口也不更新白名单，继续受产品原字段与已售冻结规则约束。运行时复用登记 URL 校验，HTTP 回调仅允许登记规则中的本地模拟主机，且还需显式 `OIDC_ALLOW_HTTP_DEVELOPMENT=true`。授权完整 URI 精确匹配，兑换再匹配同一码记录中的 URI。

应用访问 URL、集成管理 API URL、OIDC redirect_uri 和第三方登录入口分别承担不同角色，不能互换。返回 redirect_url 时用结构化 URL 构造追加 code/state，禁止字符串拼接注入；非法回调不重定向到请求提供的地址。

首次 POST 返回 `client_id`、一次性 `client_secret`、`issuer`、`redirect_uris`、`status`、`secret_available_once=true`；重复 POST 返回相同客户端，secret 为 null、一次性标志为 false，不轮换密钥。secret 为高熵随机值，数据库只存 SHA-256 secret_hash，通过 `secrets.compare_digest` 比较。响应 no-store，审计不记录密钥；当前没有 secret 恢复或轮换接口。

## 5. RS256 与密钥持久化要求

人员 JWT 使用 RS256，不能将共享 HMAC/JWT_SECRET 当成 OIDC 公钥发布。验签方限定算法、issuer、audience 和 token 用途，不接受 `none`、算法混淆或 token 内任意 jku/x5u 指定的密钥来源。

实际从 `OIDC_SIGNING_KEY_PEM` 读取持久 Secret 注入的 RSA 私钥，要求至少 2048 位、不带密码；不会自动生成或写数据库/临时文件。缺失、格式错误、非 RSA 或长度不足返回 503。内存缓存只缓存解析结果，不承担持久化；部署必须让各副本/重启使用同一受保护 Secret，不把 PEM 写入镜像、Git、接入下载或日志。kid 由公钥模数 n 的 SHA-256 前 24 位生成，同一公钥稳定。

issuer 只来自 `OIDC_ISSUER`，去掉尾部 `/`，不由请求 Host 动态推导；要求完整主机、无凭据/query/fragment，默认必须 HTTPS。仅显式 `OIDC_ALLOW_HTTP_DEVELOPMENT=true` 才允许开发 HTTP，不能误带到生产。发现端点、JWKS 和协议请求均检查对应配置；开发开关不表示 TLS 或生产配置已经验收。

JWKS 只公开 `kty`、`kid`、`use`/`alg` 和 RSA 公钥参数；私钥、数据库原始密钥记录不进入接口、接入下载、审计或测试产物。

应验收同一 token 跨 API 副本有效、重启后旧 token 仍可验证及 kid 稳定。当前 JWKS 只返回注入密钥对应的一把公钥，无内建轮换接口或旧公钥保留集合；Secret 替换不能直接宣称为平滑轮换。后续轮换须保留旧公钥覆盖已签 token 有效期及约定时钟容差。第三方仅从可信发行者的 JWKS 获取公钥，遇未知 kid 可有限刷新，不能无限重试或跳过验签。

## 6. 授权码与三阶段权限复核

### 6.1 授权码安全

实际 code 由 Authlib 授权码 Grant 生成，120 秒有效；数据库主键为 code 的 SHA-256，记录 client、user、enterprise、subscription、redirect_uri、scope、nonce/nonce_hash、S256 challenge、auth_time、expires_at、consumed_at、access_hash/access_expires_at 和 revoked_at。产品和租户由 client/订阅关联解析，不额外冻结任意调用方参数。同一 client+nonce_hash 有唯一约束；nonce 不可复用，state 由协议响应返回但不持久化为 RP 会话。

兑换查询使用 `SELECT ... FOR UPDATE`，消费时再以 `consumed_at IS NULL` 条件更新并要求 rowcount=1，和 access_hash 保存及审计在同一事务提交；异常回滚。已成功消费的 code 再次查询会设置 revoked_at 并返回 invalid_grant，从而使关联 access_token 的 userinfo 失效；已签 ID Token 的离线有效性不会因此即时消失。未成功兑换的错误请求不恢复已用 code。PG 下并发单次消费和回滚仍须由实测证据确认，不以代码锁存在推定 passed。

PKCE 只接受 S256，并验证合法 verifier 及其 SHA-256/base64url 结果；不能降级 plain。PKCE 不替代 client_secret、state 或 nonce，它们保护不同边界。[PKCE RFC 7636](https://www.rfc-editor.org/rfc/rfc7636#section-4)

### 6.2 用户、企业、应用和租户绑定

授权、兑换和 userinfo 都核查当前服务端状态，不能只相信已签 token 的旧 claims：

- 平台用户存在且启用、实名/激活状态符合业务规则。
- 对目标 enterprise 的真实 active membership；不能只使用当前企业选择器、其他企业管理员身份或 token 中历史角色。
- 产品属于支持的 SaaS 租户交付域，人员客户端 active 且与产品绑定。
- 买方企业、产品/订阅组合和真实外部租户一致；订阅有效且当前服务期有权益，未来付费段不能提前授予当前失效段访问。
- `SaaSCombinationBinding` 定位的订阅 active、external_tenant_id 非空，企业/产品与请求一致，starts_at 已到且 expires_at 未到；当前 entitlement 必须为 tenant_access 且 version_id 与订阅一致。只 paid、只有未来段或版本不匹配不能通过。
- 同一企业的 active `super_admin`/`enterprise_admin` 成员可访问其有效 SaaS 组合，无需额外 ApplicationAccessGrant；其他成员必须同时命中 active grant 的 enterprise_id、product_id、user_id 三重绑定。另一个企业的管理员角色或其他用户/产品的 grant 不授予访问。

实际绑定链为 OIDC client→product、code→user/enterprise/subscription、订阅→external_tenant_id；subject 类型为 public，sub 是平台 user.id。兑换与 userinfo 再次传入 code 原 subscription_id，组合若换绑其他订阅即拒绝。企业切换不能改变既有 token 的租户解释。当前 eligible 不要求外部用户映射表或 app_id；外部账号映射、第三方会话与对应授权隔离由 TRD-BE-015 补齐，不能将应用 grant 当成第三方账号已同步证据。

普通成员只有在获该 SaaS 应用授权时才能 SSO；这不赋予文件下载、API 密钥读取、订单管理、支付或退款权限。SSO 入口权限与原订单管理管理员权限是不同政策。

用户禁用、membership 撤销、普通成员 grant 撤销、租户关闭或订阅到期会在兑换/userinfo 的 eligible 复核拒绝；客户端停用也被重新查询拒绝。安全下架状态 `security_unpublished` 在三条链路统一拒绝，普通手动下架为草稿不取消已有订阅访问。管理员访问来自管理员成员身份，不因删除普通成员 grant 而自动消失。离线验证 ID Token 不会自动感知撤权，第三方现存 session 的再校验间隔、到期和退出策略也需明确，不能声称平台 userinfo 复核等于第三方会话即时撤销。

## 7. state、nonce 与第三方职责

| 数据 | 生成及保存责任 | 校验责任 | 不能替代什么 |
| --- | --- | --- | --- |
| state | RP 每次登录生成随机值并绑定自身登录事务/浏览器会话 | RP 回调精确比较并一次性消费；OP 保留并按协议返回 | 不证明 token 签名，不等于 PKCE |
| nonce | RP 生成并保存；OP 绑定 code 并放入相应 ID Token | RP 验证 ID Token nonce 与当前事务一致 | 不代表授权企业/租户，不等于 state |
| verifier/challenge | RP 保存 verifier，仅把 S256 challenge 交给 OP | OP token 兑换验证 verifier | 不替代 client 认证、state 或 nonce |

平台能校验参数存在/格式并绑定授权码，但仅原样返回 state 不能证明 RP 的 CSRF 校验已经执行。第三方不得接受跨浏览器、跨企业选择或已完成事务的回调。

RP 后端交换 code 后必须用可信 JWKS 验证 ID Token RS256 签名、精确 iss、aud/必要时 azp、exp/iat 与有限时钟容差、nonce，再核对应用、企业、租户和用户映射。若调用 userinfo，返回 sub 必须与 ID Token 一致。不能只 base64 解码、只看 HTTP 200 或只读取 email 后创建账户。[OIDC ID Token 验证](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation)

第三方成功后建立独立 HttpOnly、Secure 和适当 SameSite 的 session，执行本地会话固定防护；不会自动获得平台控制台 session。客户端密钥/token 留在服务端；回调 code/state 是协议参数，但不能将 access_token、ID Token、平台 Bearer 或 secret 写入跳转 query、localStorage、截图、日志或验收 JSON。回调页及时清理 URL，避免把短期 code 泄漏给第三方资源及 Referrer。
