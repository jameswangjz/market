# 系统维护前端与执行设计

## 入口与业务范围

平台系统管理员进入系统设置→系统维护，提供且仅提供4个按钮：刷新状态、Redis维护准备、Redis维护后恢复、Redis异常重启恢复。平台运营等其他角色无入口且接口返回403。

- 刷新状态：提交只读检查任务，不直接修改计费来源。页面读取PostgreSQL中缓存的来源、持久化、缺口及采集Worker状态。
- 维护准备：核对当前来源和持久化，数据库备份成功后暂停计费、排空并封存，再次校验；成功后提示可按基础设施流程停机。不会关闭、重启Redis或整机。
- 维护后恢复：重新读取真实来源和封存证据，备份后恢复原分代，核对恢复后采集Worker的新成功心跳。允许在采集已暂停时执行，不错误地要求其先就绪。
- 异常重启恢复：必须填写原因、勾选接受未知缺口并二次确认；仅连续性无法证明时备份后open，保留旧流、旧游标与未知缺口。当前来源健康时拒绝换代。

维护准备与恢复可以跨服务/虚拟机停机执行。关机、启动及Redis重启仍由基础设施工具完成。恢复校验失败保持保护，不自动转异常恢复、不清空用量。

## 技术与权限边界

前端→现有FastAPI鉴权接口→PostgreSQL任务队列→独立redis-maintenance-worker。队列和进度不依赖Redis。

维护执行器只使用PostgreSQL与Redis连接，不使用SSH、kubectl或K8S管理API，不挂载ServiceAccount Token，不配置K8S管理Role；以UID/GID 1000、只读根文件系统运行。数据库备份由执行器中的pg_dump客户端直接连接数据库，pg_restore --list校验归档，并生成SHA256；密码只在进程环境中传递，不写入参数、任务结果或日志。

新增redis-maintenance-data PVC 5Gi保存数据库归档及任务证据；与数据库任务状态共同持久化。不依赖容器/tmp保存维护结论。执行器镜像基于已审核API代码增加PostgreSQL客户端和既有只读来源检查脚本，不重复实现计费连续性算法。

## 数据与接口

- redis_maintenance_tasks：任务号、操作、状态、步骤、原因、操作人员、幂等请求标识、错误及生命周期时间。
- redis_maintenance_state：最近来源检查快照及执行器采集时间。
- redis_collector_health：计费采集Worker的独立就绪/暂停状态与心跳；状态写入失败不被当成采集成功。
- GET /api/admin/maintenance/redis：只读PG缓存、活动任务及最近20条记录，不在API请求中执行运维或等待Redis。
- POST /api/admin/maintenance/redis/tasks：仅允许inspect/prepare/resume/recover，修改动作必须填写原因，recover必须accept_gap=true。拒绝restart、stop或任意命令参数。

同一请求标识重试返回同一任务；标识复用于不同请求返回409。排队/执行期间拒绝其他任务。请求超过5分钟未开始，执行器拒绝过期动作，避免系统恢复后突然执行陈旧请求。

## 执行与故障保护

- 任务状态：queued→running→succeeded/failed；执行器中断留下的running任务在取得数据库排他执行锁后转manual_review，不自动重放。
- 队列提交使用PG事务级咨询锁；执行器持有PG会话级排他锁并核对会话身份，防止多副本重复执行。
- 每个步骤开始、完成及异常均落PG；封存/恢复/新分代另有来源审计；执行结果写入PVC证据。只读检查不创建假计费事实。
- 原因、人员、请求、开始、完成、失败、中断和步骤结果可在维护记录/审计日志中查验。前端不提供数据库备份下载或容器内部路径。
- 执行器SQL设置语句和锁等待时限，备份子进程有超时；不使用会杀死正常长备份的短心跳存活探针。
- 前端只有活动任务时每3秒查询；离开页面停止轮询，空闲不持续轮询。来源快照超过90秒不允许据此发起修改，服务端执行前仍重新核查实际状态。
- 不应同时运行主机CLI维护与网页维护；root直接操作不属于网页的排他权限范围。任何回退不得删除新增表、证据PVC或已有备份。

## 验证安排

先执行隔离HTTP权限/状态机/失败停止/幂等/中断测试，再做计费Worker和来源分代定向回归；前端执行编译、按钮门控、弹框、重试键及轮询清理测试。部署后执行真实只读任务、PG任务落库、采集心跳和备份客户端验证。不得为展示页面而直接停机、重启业务Redis或制造真实计费缺口。
