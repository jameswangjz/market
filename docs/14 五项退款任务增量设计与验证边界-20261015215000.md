# 五项退款任务增量设计与验证边界

## 本批范围

继续 TRD-R3-BE-011、BE-012、FE-008、QA-005、QA-006。只做退款及清算分组测试，不逐个功能重复全平台回归。待验收与用户验收完成严格区分。

## 有限 API 已失效权益

退款金额和回收次数继续采用已审批冻结方案。对于同一订单、同一经济段中已经结束的订阅月，允许将有完整用量证据的未用额度记录为已失效权益，先从该部分抵扣应回收次数，再减少该订单仍有效的额度。不恢复已用次数、不停用企业共享凭据、不修改无关订单权益。

资源计划保存每个订阅月的原额度、已用量、回收次数、剩余额度及认定类别；计划摘要、Redis 原子回执和不可变数据库记录共同绑定该认定。Lua 使用 Redis TIME 再次验证过期，要求零基线覆盖、同一来源进程、已知用量不倒退、并发用量不超过新额度。任何证据缺失或归属歧义继续拒绝自动执行，而不是按零用量放行。

## 退款前端

增加批准、执行中、资源回收、资金待处理、失败、重试、完成的连续状态验证；重复点击只提交一次，网络错误重试沿用幂等键，授权执行重试使用最新版本。普通企业仅查看进展，不能执行平台退款。模拟资金始终明确不代表银行到账。

截图复核发现已完成记录仍可能显示历史失败提示。修正仅对明确 completed/succeeded 的执行及资金腿隐藏历史失败文案；失败及未知状态继续展示安全提示，不显示原始异常或秘密。

## 强制终止与月清算

在临时 PostgreSQL schema 中运行实际工作进程：一笔模拟资金腿提交后，通过握手确认持久化，SIGKILL 子进程，再由新进程续跑，验证原回执不变、无重复资金腿、完成记录唯一。不是在数据库提交进行中断电，也不是银行重复扣款测试。

跨年夹具覆盖原月已付款批次、版本变更经济双腿、次月两次部分退款、冻结成本冲回、五方负向金额、报表及 CSV、未确认批次重建复用。版本变更历史明确为合成持久证据；资源适配器为模拟，不冒充实际 APISIX 或第三方链路。

## 仍需跟踪

- SaaS 原订单之后有独立续费段时，缩短共享租户到期时间可能误改后续权益；未确认处理规则前保留拒绝自动执行及人工处理。
- 缺少可信历史计量、人工核定、文件及线下退款的自动资源回收方案不以本批新增能力代替。
- 真实 APISIX 网络退款、第三方资源故障及完整浏览器申请到月度清算链路继续单列验证，不能由模型或组件测试冒充。
- 真实银行退款按用户要求留到在线支付接入后测试。

所有测试只清理明确归属的夹具，受保护订单 ORD-261012005144E1B3 及产品不修改。
