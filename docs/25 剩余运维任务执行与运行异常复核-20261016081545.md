## 4. 运行复核与 Redis 异常

业务部署标签：`20261016005810-5706151`；业务提交：`5706151e08a177f0a9219bcb182391dc114d3f7d`。API、Web、消息、交付、退款、版本变更就绪；API 与 console HTTP 均为 200。后端全部 81 个 Python 源码文件与安装版本一致。

发现 API 计费采集 worker 循环失败，readiness 未通过。只读定位结果：数据库保留旧 Redis run_id 与采集游标；当前 Redis run_id 不同，来源 epoch 不存在，计费流长度为 0。因此 `api_charge_ledger.ingest` 按设计拒绝不连续来源，日志的 online_delivery_worker 名称来自共用执行循环，不表示交付服务本身发生相同故障。

没有清空账本、游标或共享 Redis；没有把缺失调用当作零用量。历史已入库计费事实保留，但跨越该缺口的自动退款不可据此保证。不得仅重启 worker 或覆盖旧 run_id 来冒称恢复完整连续计费。

进一步只读检查发现 `market-redis` Deployment 没有 volumes/volumeMounts，当前 Redis 未挂持久卷。容器重建后无法依赖该配置保留计费流；后续修复还应增加持久化和备份/恢复验证，而不是只修改进程状态。该配置检查不等于证明已丢失业务金额，实际缺口须按原始来源与数据库事实核定。

已请求用户确认：新增计费来源换代和缺口审计修复，保留历史、验证新旧来源边界后恢复新采集；缺证历史订单继续人工核定。确认前只保留安全拦截，不执行来源重置。

证据：[40 部署实时复核](evidence/40-release-live-20261016081035.json)、[43 归档清单](evidence/43-release-archive-20261016081630/manifest.json)。清单明确 `passed_with_findings`、`release_ready=false`，不把先前实际链路通过扩展为当前全部健康。
