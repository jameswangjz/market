# 普通退款月度负清算接入设计

文档编号：07。生成时间：2026-10-15 20:17:02，北京时间（UTC+8）。

## 范围与任务

承接TRD-R3-BE-012已完成的资源先回收、资金模拟确认、持久完成证据，实现TRD-R3-BE-013普通退款负向清算。TRD-R3-QA-006负责其与既有版本变更调整的组合验证。实际银行支付仍不在本轮范围。

## 冻结经济依据

1. 仅处理普通来源、已完成且存在可信执行完成证据的退款。审批通过或执行失败不能进入清算。
2. 金额依据退款完成时绑定的不可变经济方案，不重新读取最新产品价格、版本成本或全局清算规则。资金退还顺序不决定经济分账归属。
3. 原始经济段按累计退款比例冲回冻结成本，本次成本冲回等于累计值减此前累计值；变更后的经济段使用切换时冻结的剩余收入、成本和规则。同一历史调用和原版本已冲回部分不得再次扣算。
4. 收入、成本、利润均为带符号金额。五方分账按冻结规则计算，舍入差额归入提供方，保证五方合计等于可分配利润冲回金额；累计部分退款不能因逐次舍入超额冲回。

## 数据与事务

退款对应唯一负向清算单，保留退款ID、执行ID、计划哈希及关联清算单的证据映射。数据库唯一约束与行锁共同防止重复生成；失败时整笔生成、关联与审计回滚，不能吞掉冲突并提交半成品。

既有完成证据保持不可变，不把pending_be013原始证据覆盖为新值。当前清算进展由新增关联记录推导，必须区分已生成负单、已纳入批次与已付款。

普通退款完成事务同时写入关联该退款ID的计量事件。事件幂等键为退款ID加完成动作，不以“订单最后一笔退款”推测对象。计量或审计失败必须回滚本次完成状态、完成证据和计量事件，已成功的模拟资金腿仍保留，授权重试不能重复退钱。

## 月度归属与旧批次

普通已支付订单按支付确认日期归属月份；普通退款按完成退款日期归属月份。跨月退款不重写原月已确认或已付款批次，而在完成月计入负向金额。按订单筛选生成批次时，退款同样受筛选约束。

未确认批次可依既有规则重生成，旧行作废并复用同一退款经济负单，不能重复计入有效行。已确认及付款中的批次不得重生成或改写。版本降级已有经济双腿，继续由版本变更模块纳入批次，不额外生成通用退款负单。

## 展示与权限

复用现有清算单、五方明细、月度/产品/参与方报表及下载，提供关联原订单号和退款证据说明。提供方仅查看本企业相关数据；买方退款详情不得泄漏成本、上游地址、资金源标识或内部经济快照。清算生成仍由原有清算操作权限控制，不能通过退款查看权限发起清算。

## 分组验证

- 定向：冻结规则/成本、原段与切换段、累计分币、证据缺失拒绝、重复生成和事务回滚。
- 组合：真实隔离Redis退款执行到月批次、跨月正负合计、五方报表、订单筛选、未确认重建、已确认保护、降级不重计。
- PostgreSQL：仅自有临时schema验证幂等及并发约束；不得修改受保护订单及客户真实清算数据。
- 部署后：安装版本、健康与只读权限检查；没有执行实际业务退款，不将模拟/隔离测试描述为银行或真实供应商验证。

开发进度仅根据真实代码、测试和部署结果更新。最终前端验收由用户进行，本设计不代表任务已完成。
