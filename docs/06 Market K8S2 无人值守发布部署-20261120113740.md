# Market K8S2 无人值守发布部署手册

## 1. 工作方式

K8S1 Forgejo 在 main 发布应用镜像及 OCI 包。K8S2 Harbor 的既有定时复制规则先把制品拉到本地仓库。K8S2 的 market-release-promotion CronJob 每分钟读取本地 Harbor 的 market/market-release 标签，发现更新且完整的版本后推进 Flux。K8S2 只访问现有本地 Harbor 和集群 API，运行期间使用固定摘要的 Market API 镜像。

~~~text
Forgejo main → K8S1 Harbor → K8S2 Harbor
    → K8S2 定时发布任务核验整套制品
    → Flux OCIRepository + 四个 Kustomization
    → API → Worker / Web → Jobs
~~~

发布任务按标签和摘要核对六个镜像。OCI 包必须来自预期 Forgejo 仓库的 main 提交，附带发布清单、镜像摘要及清单校验值。任务还检查候选版本支持站点使用的数据库类型。镜像未全部同步时保留现行版本，下一轮继续检查。当前采用定时检测。 [OCI 标签列表与分页](https://github.com/opencontainers/distribution-spec/blob/main/spec.md#listing-tags)

确认候选版本后，任务先保存当前版本和镜像映射，再暂停四个 Kustomization，同步写入新的镜像映射和 OCI 摘要。source-controller 就绪后放行 API。API 对本次摘要就绪后，放行 Worker 和 Web，最后放行 Jobs。每次等待都检查实际应用的摘要和资源的观测代数。CronJob 的并发策略与 Kubernetes Lease 防止多个实例同时推进。每阶段状态保存在 ConfigMap，任务中断后下一轮续跑。 [Flux Kustomization 依赖与健康检查](https://fluxcd.io/flux/components/kustomize/kustomizations/#dependencies) · [Kubernetes CronJob 并发策略](https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/#concurrency-policy)

## 2. 安装前条件

| 项目 | 现场应具备 |
| --- | --- |
| Harbor | 目标私有项目 market 已配置复制。OCI 发布包存于 market/market-release，其余六个组件镜像按同一发布标签同步 |
| Flux | source-controller 和 kustomize-controller 已就绪。指定 OCIRepository 为 market-release，四个 Kustomization 为 market-api、market-workers、market-web、market-jobs |
| 应用基线 | 四个阶段均已应用同一摘要并就绪，镜像映射指向目标 Harbor。应用安装在 market 命名空间 |
| 账户及证书 | flux-system 中存在 market-harbor-pull 与 market-harbor-ca，分别是目标项目的只读登录凭据和 CA |
| 运行镜像 | 目标 Harbor 中的 Market API 镜像，使用 sha256 摘要。镜像提供 Python 和 PyYAML |
| 数据库 | 站点以 Postgres 或 Dameng 设置兼容门禁。示例 K8S2 使用 PostgreSQL |
| 移交 | 在有 Git 的管理机上导出下述安装脚本及 Kubernetes 定义，把归档送往 K8S2 |

安装前先检查控制面与现场版本。

~~~bash
kubectl config current-context
kubectl -n flux-system get deployments source-controller kustomize-controller
kubectl -n flux-system get ocirepository,kustomization
kubectl -n market get deployment market-api -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
~~~

## 3. 安装与启用

从已检出本功能的源码目录生成安装归档。

~~~bash
git archive -o market-release-promotion.tar HEAD \
  k8s/market-release-promotion.yaml \
  scripts/install_market_release_promotion.py \
  scripts/promote_market_release.py \
  scripts/market_release_bundle.py \
  scripts/verify_market_release.py
sha256sum market-release-promotion.tar > market-release-promotion.tar.sha256
~~~

将归档和校验文件传到 K8S2。以下命令复用 K8S2 正在运行的 API 镜像，并先进行服务端试运行。安装器默认创建暂停的 CronJob。重新安装会保留现有 ConfigMap 状态和 Lease，应用新的任务定义后需再次确认启用。若处在发布中途，先暂停发布并等待执行中的 Job 退出，再更新任务定义。

~~~bash
umask 077
directory=/root/market/ops/market-env2/release-promotion
install -d -m 0700 "$directory"
cd "$directory"
sha256sum -c market-release-promotion.tar.sha256
tar -xf market-release-promotion.tar

registry=192.168.10.17:30443
image=$(kubectl -n market get deploy market-api -o jsonpath='{.spec.template.spec.containers[0].image}')
python3 -B scripts/install_market_release_promotion.py \
  --registry "$registry" --image "$image" --db-type Postgres --dry-run
python3 -B scripts/install_market_release_promotion.py \
  --registry "$registry" --image "$image" --db-type Postgres
~~~

确认安装成功后，可派发一个首次检查 Job。它会读取 Harbor 并记录现行基线。如果 Harbor 已有更高且完整的版本，这个 Job 会按正式流程推进。按原版本进行无变更验收时，先确认本地仓库最新发布和正在运行的摘要一致。

~~~bash
job="market-promotion-check-$(date +%H%M%S)"
kubectl -n flux-system create job "$job" --from=cronjob/market-release-promotion
kubectl -n flux-system wait "job/$job" --for=condition=Complete --timeout=120s
kubectl -n flux-system logs "job/$job"
~~~

正式启用如下。源 Harbor 的复制仍使用现场既有时间表。目标 Harbor 中整套制品核验通过后的调和由发布任务自动推进。

~~~bash
kubectl -n flux-system patch configmap market-release-promotion-state \
  --type=merge -p '{"data":{"paused":"false"}}'
kubectl -n flux-system patch cronjob market-release-promotion \
  --type=merge -p '{"spec":{"suspend":false}}'
kubectl -n flux-system get cronjob market-release-promotion
~~~

## 4. 查看发布状态

~~~bash
kubectl -n flux-system get cronjob market-release-promotion
kubectl -n flux-system get jobs -l app.kubernetes.io/name=market-release-promotion
kubectl -n flux-system get configmap market-release-promotion-state \
  -o jsonpath='{.data.state\.json}{"\n"}' | python3 -m json.tool
kubectl -n flux-system get ocirepository market-release
kubectl -n flux-system get kustomization \
  -o 'custom-columns=NAME:.metadata.name,APPLIED:.status.lastAppliedRevision'
kubectl -n market get deployments
~~~

也可从 CronJob 名称前缀选取最新 Job 并读取 kubectl logs。发布成功的依据是任务记录 deployed、状态中 active 指向新版本且 pending 已清除、OCI 源和四阶段都为 Ready，四阶段的 lastAppliedRevision 一致。

| 状态或日志关键字 | 含义 |
| --- | --- |
| up_to_date | 当前为最新合规版本。本次没有修改 Flux |
| waiting_for_complete_release | 候选发布至少有一个镜像或标签未通过核验。下一轮复查 |
| verified_release、flux_source_selected | 已核验并记录发布计划，正在切换 OCI 源 |
| waiting_for_source、waiting_for_stage | 当前阶段尚未达到本次摘要的就绪状态，继续等待 |
| deployed | 四阶段均确认应用了新摘要，记录现行版本及可用于回退的前一版本映射 |
| promotion_blocked | 计划已超过 25 分钟。未放行的阶段保持暂停，运维需检查 Flux 状态 |
| paused、flux_suspended、release_held | 运维暂停了发布，Flux 当前暂停，或该版本落在运维指定的跳过范围内 |
| promotion_stopped | 发布身份、站点配置或既有摘要与受管状态冲突。先读日志和 ConfigMap 再处理 |

出现缺镜像时，先查 K8S2 Harbor 复制任务、版本标签和摘要。出现部署等待时，查对应 Kustomization 的 describe 和受管 Deployment 的日志、探针与 Pod 事件。目标 Harbor 单个制品出现或上报事件仅表示候选可检查。 [验证 OCIRepository 状态](https://fluxcd.io/flux/components/source/ocirepositories/)

## 5. 暂停、恢复与计划停机

临时止住自动发版时，先给状态加暂停，再暂停 CronJob。等待已有 Job 退出后，再操作源摘要、Flux 阶段或应用副本。单独暂停自动发版时，已经运行的 Market 保持服务。

~~~bash
kubectl -n flux-system patch configmap market-release-promotion-state \
  --type=merge -p '{"data":{"paused":"true"}}'
kubectl -n flux-system patch cronjob market-release-promotion \
  --type=merge -p '{"spec":{"suspend":true}}'
kubectl -n flux-system get jobs -o custom-columns=NAME:.metadata.name,ACTIVE:.status.active
~~~

继续此前待部署的同一计划时，检查当前状态及站点配置，再使用第 3 节的启用命令。整套 Market 计划停机时，还需要暂停对应 Flux Kustomization 和应用定时任务，并按业务停机步骤缩容及维护 Redis。应用启动和业务检查完成后再恢复自动发版。

## 6. 发布异常与回退

1. 按第 5 节暂停，待活动 Job 结束后，导出 ConfigMap 的 state.json 留存。本轮尚未完成时，active 记录切换前的版本，pending.previous_images 为切换前的四阶段映射。已完成时，rollback.active 和 rollback.images 记录上一个版本。
2. 判断数据库 Schema 和业务数据能否被旧应用读取。确认后按独立部署手册回退流程冻结四个阶段，用保存的旧摘要和四阶段镜像映射恢复同版配置，随后按依赖恢复 Flux，并执行业务冒烟。发布任务保留现场状态供检查，数据库恢复依原有运维流程执行。
3. 回退成功且决定跳过该问题发布时，人工指定 skip-through 为要跳过的版本，清空发行任务内部状态，使它从已经验证就绪的回退版本重新建立基线。保留暂停直到操作复核完成。只有比 skip-through 时间戳更晚的合规版本才会再次自动部署。

以下为第 3 步示例，须将版本替换为已复核的待跳过版本。

~~~bash
read -r -p '要跳过到哪个版本（YYYYMMDDHHMMSS-GitSha）: ' failed_version
patch=$(python3 - "$failed_version" <<'PY'
import json, sys
print(json.dumps({"data":{"paused":"true","state.json":"{}","skip-through":sys.argv[1]}}))
PY
)
kubectl -n flux-system patch configmap market-release-promotion-state --type=merge -p "$patch"
~~~

确认状态后按第 3 节恢复自动任务。现行应用仍以 Flux 中已核验的摘要为准。

## 7. 权限和维护

安装器创建专用 ServiceAccount、Role 和 RoleBinding。发布任务可读取本地 Harbor 制品，可在部署命名空间读取及更新指定 OCIRepository、四个 Kustomization、状态 ConfigMap 和 Lease。应用发布包、签名或仓库写权限由现有 Forgejo 和 Harbor 管理。安装脚本和配置不包含仓库密码。类生产站点应维护现有镜像留存策略，供正在运行版本和必要的回退版本按摘要拉取。
