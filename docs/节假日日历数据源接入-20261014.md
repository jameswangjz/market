# 节假日日历数据源接入

日期：2026-10-14。本文说明本批实现；不代表已部署或已完成全部 BE-009。

## 来源与许可

采用 [cg-zhou/holiday-calendar](https://github.com/cg-zhou/holiday-calendar) 的原始年度静态 JSON，项目使用 [MIT 许可](https://github.com/cg-zhou/holiday-calendar/blob/main/LICENSE)。不引入其 JavaScript 库，不复制库代码。

固定地址：`https://raw.githubusercontent.com/cg-zhou/holiday-calendar/main/data/CN/{year}.json`。
根字段为整数 `year`、`region="CN"`、非空 `dates` 数组；日期项仅接受 `public_holiday` 或 `transfer_workday`，要求合法 ISO 日期、年份一致、日期不重复。内容按规范化 JSON 计算 SHA-256；来源内容仍需上游维护，校验通过不等同平台独立核实国务院公告。

## 缓存与接口

- `holiday_calendar_versions`：保存年度、区域、规范化内容、内容 hash、固定来源 URL、首次取回时间。同内容幂等，保留全部历史版本。
- `holiday_calendar_states`：保存每年当前版本指针、最近检查时间、同步状态与脱敏失败原因。
- `GET /api/sla/holiday-calendars?year=2026`：查看缓存状态和历史版本；省略年份列出已检查年份。
- `POST /api/sla/holiday-calendars/2026/sync`：手动同步。两个接口均仅允许 `super_admin`、`platform_operator`，年份范围 2000–2100。
- 上游失败返回明确的 `sync_status=error`；404 为 `notpublished`。接口使用 HTTP 200 表示同步尝试已记录，调用方必须检查状态，不可仅凭 HTTP 状态判断数据可用。
- 失败或 404 不清空已有版本。`cache_status=available` 仅表示该年度存在通过校验的缓存；不代表所有年份齐全或源刚刚同步成功。

请求只访问固定 HTTPS 来源，禁用重定向和环境代理，拒绝压缩响应；连接/读取等阶段超时为 5 秒，流式读取检查 15 秒总预算，最多 128 KiB、366 个日期项。下载预算检查在每次读取后执行，总耗时还受单次读取超时约束。

## 调度与告警

`scripts/sla_calendar_sync.py` 与镜像内 `python -m app.holiday_calendar` 使用同一入口。CronJob 每天北京时间 03:15 检查当年及下一年，两个年度独立提交；不必等到元旦才取回数据。镜像标签由发布方替换，不部署浮动占位标签。

下一年 404 记录 `notpublished`，不作为故障告警。同步 `error` 即使保留旧缓存也向系统管理员/平台运营发站内告警；当年 404 且无可用缓存同样告警。幂等键按年份、状态和北京时间日期组成。通知使用既有事务内消息/Outbox；同步 worker 对 `error` 返回非零退出码。

CronJob 仅加载 `market-config` 和单独的 `JWT_SECRET`，不注入整份 `market-secrets`。数据库使用既有配置；脚本不执行建表或启动种子数据。API 应先启动并按既有 `Base.metadata.create_all` 流程创建新增缓存表。

## 快照及接入

主 Agent 在 main 末尾按以下顺序安装，安装动作本身不取回数据：

```python
from .holiday_calendar import install as install_holiday_calendar
holiday_calendar = install_holiday_calendar(globals())
# 随后安装 enterprise_sla，再安装 after_sales_workflow。
```

`enrich_support_calendar(db, base_calendar)` 仅查询缓存，返回独立 JSON 字典。`covered_years` 只含当前缓存指向且通过内容 hash 校验的年度；不向未发布年度复制假期。战略级 `exclude_public_holidays=False` 不需要年度配置，也不查询缓存。

`enterprise_sla.freeze_sla_snapshot` 已调用增强 hook。`contract_rule_version` 标识未附加外部年度数据的承诺定义；`calendar_content_hash` 标识实际增强后的日历内容；`rule_version` 覆盖最终完整规则和增强后的日历。缓存变化只影响以后创建的新快照，不回写原工单的 `sla_snapshot_json`。

本小批不提供 `resolve_ticket_calendar` 或工单跨年绑定表。创建时尚未发布的未来年度，仍需后续独立、审计化的年度版本绑定机制；不得把现有快照替换成实时缓存来消除未就绪状态。父 Agent 的工单惰性绑定及 SLA GET 提交边界需独立验证，不属于本批缓存测试。

## 验证边界

本批采用 mock HTTPS 与隔离 SQLite，覆盖权限、年份、源校验、下载限制、内容幂等、历史保留、失败/404 保留缓存、年度覆盖、战略级例外、告警幂等和快照 hash。真实上游取回、VM 网络、PostgreSQL 并发及 CronJob 部署由父 Agent 验证；未伪造真实年度假期。
