## 5. 性能与测试边界

同一 API Pod、相同 Redis 版本，100 次预热后测 1000 组 64 字节 SET/GET：

| 配置 | P50 | P95 | P99 |
| --- | --- | --- | --- |
| 开启 AOF 前 | 1.254ms | 1.669ms | 1.959ms |
| 开启 AOF 后 | 1.172ms | 1.587ms | 1.856ms |

该样本未见明显退化，差异不代表 AOF 能提升性能；不是高并发、长时间重写或整个平台容量证明。测试键精确清理，未使用全局 FLUSH。证据：[55](evidence/55-redis-performance-before-20261016133640.json)、[56](evidence/56-redis-performance-after-20261016133640.json)。

专项测试：后端/Lua 172 项、原生夹具/清理 123 项、重启验证器 22 项、迁移/配置/基准/审核门禁 25 项通过。Lua 集成单元运行时为 Redis 8.0.5；实际部署和最终重启验证为 Redis 7.4.11，分别声明，不混称同一环境。

本轮未做真实银行支付、完整浏览器交易、断电/磁盘损坏、Redis 高可用切换或持续高负载压测。AOF everysec 仍有短暂丢失窗口，单节点 local-path 不代表跨节点容灾。

## 6. 后续运维

源码工具：`scripts/redis_source_admin.py`，只允许活动的平台系统管理员身份执行，修改必须有 reason，output 必须是新路径。工具需从已验证 release/scripts 复制到当前 API Pod；不要把容器内 /tmp 当作唯一备份。

计划重启先执行 `seal`，确认成功后重启 Redis，再执行 `resume`；验证失败保持拦截并核对证据，不覆盖游标。非计划重启缺少可信封存证据时仍需管理员审查，不能盲目覆盖 run_id；确需新代次使用显式 `open` 并保留新缺口。

审计日志可检索 `redis_source_open`、`redis_source_seal`、`redis_source_resume` 和 `submit_redis_recovery_review`。不直接回退到不识别新代次的旧计费代码；回退前先封存接入、保留 PVC/数据库新表及备份并评审兼容性。
