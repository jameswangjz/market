# 订阅续费与配额阶段设计和验证

## 范围及依赖

本阶段实现 TRD-BE-009、TRD-BE-010 的订阅持久化和续费流程，推进 TRD-BE-011 新订阅配额及 TRD-FE-009 的订单订阅界面。升降级报价、资金与资源补偿、正负清算调整仍依赖 TRD-BE-016/017/018，不提前开放界面或标记完成。SaaS 首购租户和 OIDC 联调另由 TRD-BE-013/014/015 完成。

## 数据模型

| 实体 | 关键约束 | 职责 |
| --- | --- | --- |
| subscription_combinations | 企业与产品联合唯一 | 当前版本、原始月锚点、代次、累计月份 |
| subscription_terms | 订单唯一关联 | 已交付订单的独立半开有效时段、版本、所属代次 |
| subscription_renewals | 企业与请求键唯一 | 请求摘要、源订单、月份、新订单；与建单事务原子提交 |

历史订单和历史 SaaS 租户期限不自动导入或重算。新模型使用订单冻结的经济和交付快照，不重新读取目录价格、成本和额度作为已售权益。

## 日期与续费

- 交付成功时冻结原始锚点，所有月份边界从该锚点直接计算。
- 例如北京时间 1 月 31 日起购：2 月取最后一天，3 月仍回到 31 日，不从 2 月末滚动漂移。
- 使用 [开始时间, 结束时间)；精确到秒及微秒的剩余比例与原订单全时段对比，不与累计续费时长混用。
- 每次购买 1～36 个月。有效期内相同版本续费顺延；已到期重新交付成功建立新代次和锚点，保留旧时段。
- 未支付或未成功交付的续费订单不延长期限。未来已交付续费段不提前生效，不重置或叠加当前配额。
- 活跃组合不允许通过普通重复购买偷偷切换版本，需走后续版本变更流程。

## 接口与权限

- GET `/api/orders/{order_id}/subscription`：查看组合期限、当前配额周期、冻结限额、所有历史与未来时段及可续费标识。买方已实名且为已认证企业超级管理员/管理员可查看；平台超级管理员和财务可查看，不泄露成本和 Secret。
- POST `/api/orders/{order_id}/renewal`：提交 `subscription_months` 和 `idempotency_key`，创建相同版本待支付订单。相同键和参数返回原订单，参数不一致返回 409。
- 买方管理员可创建续费订单，只有企业超级管理员发起支付，平台财务保留人工到账确认。
- 订单详情展示期限、时段和续费弹框。续费失败保留请求键用于重试；前端不自动支付。

## 实际接入

API/模型 API 交付处理先验证该购买版本已发布且有有效接入证据，再执行带 SSRF 防护的健康检查。目标地址改变须重新验证，不能用对其他地址的健康结果给旧网关授权。

SaaS 必须存在匹配企业、产品、版本的已开通租户，才允许启动计时。仅设置 success 标志不是开通证明。本阶段不会借此宣称 SaaS 新首购或 SSO 已完成。

订阅授予、期限、审计、计量及消息在数据库事务内提交。Redis 只投影已提交的权益，由消息工作进程周期同步及凭据查询/创建触发刷新，避免数据库回滚后网关保留未提交的授权。新计数规则在请求时检查时段，到期拒绝不依赖后台定时任务。

## 配额

- 相同企业与产品共享组合计数，不按新增订单、凭据或不同网关副本重置。
- 订阅月配额按照原始锚点周期；每日配额按北京时间自然日；保留每分钟限流。
- 千次输入换算为整数调用次数，0 表示日/月不限；历史非整千额度保留精确值，不向上取整放大授权。
- 原生 APISIX 插件从 Redis 中选择当前有效时段，使用 Redis EVAL 原子执行计数与限额。未来、过期、重叠、无效元数据或路由不匹配均拒绝，Redis 不可用时返回 503。
- 版本变更和凭据轮换使用稳定组合及周期键保留计数。后续升降级不得重置已用量。
- 手动停用凭据不因续费而重新激活。

## 尚未关闭的门禁

已有历史用量的凭据切换新计数时，当前实现拒绝迁移而不清零。严格迁移需要稳定切换、保留历史计数及并发验证，因此 TRD-BE-011 保留进行中状态，不以新凭据测试替代旧计数迁移验收。

TRD-FE-009 仅完成期限与续费部分，升降级预览、兼容性确认、资源变更和退款进度尚未完成。

## 验证要求

1. 日历边界、半开区间、有效续费、到期重启、未来时段、冻结限额、重复请求及消息失败回滚。
2. 真正执行 Lua＋Redis 验证北京时间日界、订阅月界、并发额度、0 不限、重试及凭据轮换保持用量；跳过不计为通过。
3. 在开发环境验证 PostgreSQL 与 APISIX 联调、真实续费建单、支付、健康检查和未来时段策略。
4. PostgreSQL 独立事务并发授予和相同请求键建单；所有测试数据严格隔离及清理。
5. 浏览器检查订单期限、未来段、续费弹框的展示和权限，明确只读检查与实际写操作的验证边界。

## 本阶段实际验证结果

- 304 项后端回归通过，包括 32 项订阅时段测试和 6 项订阅网关桥接测试。
- 14 项真实 LuaJIT＋Redis 测试通过，未跳过；包括日界、月界、并发用量、计数错误拒绝及 Consumer 配置合并时的原始路由身份校验。
- 67 项前端测试及生产构建通过。订单订阅面板与续费弹框的浏览器端到端验收尚未完成，不将单元测试或已有线下履约截图作为该页面验收证据。
- 开发环境三副本原生 APISIX 验收通过：26 项检查覆盖共享限额、0 不限额、未来/过期/停用/异常时段拒绝、并发额度不超卖和拒绝请求不增加用量。切换旧计数的迁移验收仍未关闭。
- 真实 PostgreSQL 并发验证使用两个独立连接，并确认数据库阻塞后释放持有锁：两条已交付订单形成连续的 2 段、合计 5 个月；重复授予无变化，两个相同 HTTP 续费请求只产生 1 条订单及付款单；已确认隔离夹具清理。
- PostgreSQL、MinIO、ClamAV 与原生 APISIX 运行链路验证包含审核发布、买方权限、人工到账确认、实际健康验证交付、未来续费及凭据轮换保留用量。测试上游认证为 none，不据此宣称新增 OAuth/OIDC 联调完成。
- 开发环境镜像：`20261010030448-f320791`；API 1 副本、WEB 1 副本、消息工作进程 2 副本、APISIX 3 副本就绪。部署前已备份数据库，未修改用户已有测试产品。
