# 售后工单现状与状态说明

核对日期：2026-10-16。本文描述当前实现，不将设计预期、历史兼容状态或监控任务成功解释为本次业务已触发告警。

状态图：[38 售后工单状态转换图](38%20售后工单状态转换图-20261016173336.svg)。图为原生 SVG，文字、节点和路径均可编辑，无位图或外部资源，内置中文字体回退。

## 1. 谁可以创建，什么条件可以创建

创建者是订单买方企业的有效管理员成员：成员角色为 `super_admin` 或 `enterprise_admin`，成员状态为 `active`。这里的企业 `super_admin` 与平台角色同名但作用域不同；带有平台角色的用户不能以交易方身份创建工单。

- 用户须启用（`is_active`）、激活状态为 `active`，实名状态为 `verified`；买方企业认证状态须为 `verified`。
- 订单属于当前买方企业且符合请求业务作用域。前端要求支付状态为 `paid`、`refunding`、`refunded` 之一，并且 `paid_amount > 0`；后端判断这三个支付状态及已支付金额非零。
- 同一订单、同一售后类别只能有一个未结束工单；不是整张订单只能有一个工单，不同类别可并行。重复判断中 `completed`、`withdrawn`、`force_closed` 及历史 `resolved`、`closed` 视为已结束。
- 售后类别、说明去除空白后不能为空；须提供幂等键。优先级支持 `normal`、`important`、`urgent`。
- 必须能取得买方企业当前 SLA 承诺快照；未配置则拒绝创建。创建时冻结服务等级、指标规则与基础日历，后续配置变更不改写旧工单承诺。

当前创建逻辑不要求交付完成，也没有固定“支付后若干天”或“交付后若干天”的申请窗口校验。不能据此补写交付完成、固定天数等准入条件。

## 2. 状态含义

| 状态 | 含义与下一步 | 解决时钟 |
| --- | --- | --- |
| `awaiting_response` 待提供方响应 | 创建后的初始状态，等待提供方响应 | 按支持日历累计 |
| `processing` 处理中 | 提供方处理、提交方案；也承载拒绝方案后的整改 | 按支持日历累计 |
| `awaiting_buyer_info` 待买方补充材料 | 提供方要求补充材料，等待买方提交 | 暂停 |
| `awaiting_buyer_confirmation` 待买方确认 | 已提交方案，等待买方确认或拒绝 | 暂停 |
| `platform_intervention` 平台介入中 | 保存介入前状态，等待平台响应、审查 | 不因介入暂停 |
| `completed` 已完成 | 买方明确确认解决 | 结束，属于确认解决 |
| `withdrawn` 已撤回 | 买方主动撤回 | 结束，不代表确认解决 |
| `force_closed` 已强制关闭 | 平台管理员或运营强制关闭 | 结束，不代表确认解决 |

后三项为当前终态，没有继续转换或重开动作。前端兼容显示 `resolved`（已解决，历史）、`closed`（已关闭，历史）；不是当前新建流程的额外节点。工作流将历史 `resolved` 按 `completed` 检查动作权限，不补造历史响应时间或完成证据。

## 3. 完整动作与权限

表中买方、提供方均指相应订单企业的有效 `super_admin` / `enterprise_admin` 成员，企业须认证、用户须激活实名。平台介入角色为平台 `super_admin`、`platform_operator`、`delivery_monitor`；强制关闭仅限前两者。

| 动作 | 操作者 | 起点 | 终点 / 行为 |
| --- | --- | --- | --- |
| 创建 | 买方 | 符合创建条件的订单 | `awaiting_response` |
| `respond` 响应工单 | 提供方 | `awaiting_response` | `processing`，记录首次响应时间 |
| `request_info` 要求补充材料 | 提供方 | `processing` | `awaiting_buyer_info` |
| `supplement` 补充材料 | 买方 | `awaiting_buyer_info` | `processing` |
| `submit_resolution` 提交解决方案 | 提供方 | `processing` | `awaiting_buyer_confirmation` |
| `confirm` 确认解决 | 买方 | `awaiting_buyer_confirmation` | `completed` |
| `reject_resolution` 拒绝解决方案 | 买方 | `awaiting_buyer_confirmation` | `processing`，启动整改轮次 |
| `request_intervention` 申请平台介入 | 买方或提供方 | 四个常规未结束状态 | `platform_intervention`，保存 `previous_status` |
| `respond_intervention` 介入响应 | 三类平台介入角色 | `platform_intervention` | 状态不变；每轮只允许记录一次首次响应 |
| `review_intervention` 完成平台审查 | 三类平台介入角色 | `platform_intervention` | 动态恢复本轮 `previous_status` |
| `withdraw` 撤回工单 | 买方 | 全部五个未结束状态 | `withdrawn` |
| `force_close` 强制关闭 | 平台 `super_admin` / `platform_operator` | 全部五个未结束状态 | `force_closed` |

四个常规未结束状态为 `awaiting_response`、`processing`、`awaiting_buyer_info`、`awaiting_buyer_confirmation`；全部五个再加 `platform_intervention`。因此平台介入期间也可由买方撤回，或由有权限的平台角色强制关闭。`delivery_monitor` 可介入响应和审查，但不能强制关闭。

平台审查恢复的可能是上述四个常规状态中的任意一个，绝非固定回到 `processing`。原状态缺失或无效时返回冲突错误，要求核查历史。平台响应是状态自环，审查与首次响应是两个独立动作；直接审查结束也不会替代缺失的首次响应证据。

常规闭环为：创建 → 提供方响应 → 处理 → 提交方案 → 买方确认。材料回路为：处理 → 要求补充 → 买方补充 → 处理。整改回路为：待确认 → 买方拒绝 → 处理 → 再次提交方案；整改是 SLA 轮次，不是新增工单状态。

## 4. SLA 当前口径

承诺来自创建时冻结的买方企业 SLA 快照；本文不推定实际服务等级数值、响应分钟数、解决小时数或预警阈值。实际目标、预警值、规则版本、时钟类型应以工单 SLA 接口返回的快照为准。基础快照不会被刷新改写；跨年日历可按实现追加带审计的年度绑定，不等于替换冻结承诺。

| 指标 | 计时与完成依据 |
| --- | --- |
| 首次响应 | 从创建到提供方 `respond`。普通及重要优先级按支持日历；紧急按自然时间。买方等待不暂停首次响应，平台首次响应也不代替提供方首次响应。 |
| 解决 | 从创建到终止，按支持日历计量；进入待补材料或待确认期间暂停，离开这些状态恢复。进入平台介入即恢复累计，即使介入前正在等待买方；审查恢复等待状态后再次暂停。只有 `completed` 认定确认解决。紧急解决仍按支持日历。 |
| 整改 | 每次 `reject_resolution` 启动，到下一次 `submit_resolution` 结束；等待补充材料暂停，平台介入不暂停。使用冻结整改规则的时钟及阈值。 |
| 平台首次响应 | 每次申请介入独立一轮，到 `respond_intervention`；紧急使用对应紧急指标，时钟类型与阈值取冻结规则。缺少响应事件不能用审查或关单补作响应。 |
| 平台审查 | 每次申请介入到 `review_intervention`；按冻结审查规则计量，每轮保留来源事件。 |

支持时钟依据版本化日历的时区、工作日、支持时段、节假日与调休覆盖计算，不等于简单自然时间差。证据或日历不足时输出 `insufficient_data` 或部分可计量结果，不能推定达标。

`withdrawn`、`force_closed` 会终止计时，但不产生买方确认。未确认终止的指标可显示 `closed_without_confirmation`，已经超标时优先显示 `breached`；生命周期仍可为 `closed_incomplete`。缺失平台响应证据则为 `insufficient_data`。不存在“到期自动确认”“超时自动完成”的状态转换。

## 5. 审计、并发与前端表现

每次动作要求非空处理说明、`expected_version`、幂等键，可关联附件。代码锁定订单与工单并校验版本，冲突返回 409；同一用户同一幂等键重放相同请求可复用结果，挪用于不同内容或工单会拒绝。

事件保留动作、前后状态与版本、操作者及企业角色、原因、请求标识、发生时间、关联附件，并写入审计与业务通知。SLA 投影保留来源事件、规则快照、日历绑定、计量时间和版本；历史不完整时不伪造证据。前端以服务端 `allowed_actions` 为操作依据，额外限制强制关闭角色；权限不由状态名称单独推导。

订单 `after_sales_status` 是汇总字段：有未结束工单则为 `processing`，本单无其他未结束工单且本工单终止时为 `resolved`。该订单汇总不代表每张工单都被买方确认解决，也不替代工单自身状态。工单创建及状态流转本身不等于执行退款。

## 6. 运行事实边界

已核对开发环境实际安装的工作流与时钟模块文件哈希，均与当前源码一致。`ticket-sla-monitor` 未暂停，每5分钟运行，最近任务成功但 `evaluated=0`。这仅表明该次任务运行成功且没有评估对象，不能声称本轮实际触发了告警、通知或业务闭环。

本次售后工作流、首次响应与解决时钟、整改与平台介入轮次、时钟投影及阈值监控共68项隔离测试通过。修复了一条“日历缺失”测试夹具：固定支持时段内的测试时间并隔离年度日历补全，消除测试随真实执行时间变化的假失败；没有修改后端业务行为。

前端入口：买方在“订单中心”的订单操作中选择“发起售后”；后续在“交付与售后”的“售后工单”Tab查看和处理。打开工单详情，展开“工单SLA指标与来源（只读）”可查看冻结承诺、计量结果与来源事件。个人用户、企业普通成员、提供方和平台人员均不能代替买方创建。
