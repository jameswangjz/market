# 消息中心业务事件接入说明

初始业务接入仅修改 `backend/app/main.py` 并创建本文档。后续按用户新增授权保存 `backend/tests/test_message_business_events.py` 和 `scripts/test_message_business_events_pg_redis.py`。本协作者未编辑 `message_center.py`、`test_message_center.py` 或前端文件，未执行 commit、push 或部署；共享目录中其他协作者的变化不在本次编辑范围。

## 接入原则

- `notify_business_event` 直接使用约定的 `message_center['create']` 接口，传入 severity、event_key、category、tenant_id，使用调用方 Session，不自行 commit。
- 显式申请人/订阅拥有者/订单购买人、企业管理者、平台角色分开解析并去重。所有收件人必须 `is_active=True` 且 `activation_status=active`；企业管理者必须拥有 active Membership，角色为企业 super_admin 或 enterprise_admin，并且没有平台角色。既有 `notify_platform_role` 也补充 activation_status 过滤。
- 收件人为空时不创建空消息。幂等键含实体 ID（清算单/批次使用唯一业务编号）及状态、退款实体、重试次数或动作时间；超过 180 字符时使用完整键的 SHA-256 摘要。
- 消息仅包含业务状态和必要的订单编号，不复制审计 detail、before、after、身份证、手机号、凭据、异常原文或清算金额。企业申请审计 after 仅新增 applicant_user_id 用于定位申请人，消息不包含该审计快照。
- 本次没有 GET 通知入口。清算审计仅对白名单动作发消息，通知读取、确认、删除、发送等操作不在白名单，不产生循环。
- 产品审核 `notify_platform_role` 支持显式 event_key，默认使用产品 ID + 当前审核状态 + 目标角色 + flush 后的 product.updated_at；同一状态版本重复调用去重，驳回/撤回后重新进入同一阶段产生不同键。业务/质量审核通知移至审核字段全部更新后，避免发送后另一次产品更新改变来源版本。

## 事务与静态审核

一般事件写入发生在原业务 commit 前；新增 flush 只为取得申请、退款、更正、考核结果 ID，以及让清算批次关联查询看到本事务新增明细，不提交事务。业务回滚应同时撤销 Message、Receipt 与 Outbox。

SaaS 接口已有 `execute_saas_operation` 多阶段 commit：记录执行中、供应商结果和最终订单分别提交。到期通知表示已确认的旧周期到期事实，随续费操作的第一个执行记录 commit 保存，供应商续费失败仍保留该事实；支付/降级退款通知随最终订单事务保存。没有新增 commit，但供应商调用与本地最终订单并非一个原子事务，属于现有流程限制。

## 周期 Hook 与 Worker 契约

`notification_scheduled_events(db)` 定义在主文件中，位于 `install_message_center(globals())` 之前。消息中心可通过安装时的 namespace 动态读取 `ns.get('notification_scheduled_events')`；无需再次 import 主文件，也不调用 startup/seed。共享目录已有协作者提供 `scheduled_scan` 包装，本次未修改其实现；实际 worker 周期调度尚未联调。

调用契约如下，提交和异常回滚由 worker 管理：

```python
with SessionLocal() as db:
    summary = notification_scheduled_events(db)
    db.commit()
```

不要把 hook 放进每条 Outbox 消息的发送路径，也不要求每次 `process_once` 都全表扫描。由 worker 定时调用 `scheduled_scan` 或同等包装即可；多 worker 应复用消息中心包装的数据库锁和 create 的唯一 event_key。

hook 返回 `saas_candidates`、`quota_candidates`、`redis_unavailable`；前两项为符合条件的通知尝试数，不代表新增消息数，重复扫描仍可能返回相同候选数。

API 读取规则直接对应 `k8s/market-gateway-quota.lua`，使用 Redis DB 0，`REDIS_URL` 必须配置为该数据面实例的 DB 0；连接/读取超时各 1 秒。只处理有 apisix_consumer_name、关联 active 路由、未到凭据有效期的 active/exhausted 凭据，不修改凭据或订阅状态。

| Redis 来源 | 格式/用途 |
| --- | --- |
| 凭据元数据 | `market:apisix:credential:{consumer}`；status 非 active 时跳过；daily_quota/monthly_quota/total_quota 优先覆盖数据库限额 |
| 日计数 | `market:apisix:quota:day:{route_key}:{consumer}:{YYYY-MM-DD}`，UTC 日期 |
| 月计数 | `market:apisix:quota:month:{route_key}:{consumer}:{YYYY-MM}`，UTC 月份 |
| 总计数 | `market:apisix:quota:total:{route_key}:{consumer}` |

数据库日/月限额为 None 时回退路由限额；总量使用 credential.total_quota。0 为无限制，缺失计数视为 0，格式错误的单项限额/计数跳过。Lua 对被拒绝请求执行 DECR，所以持久计数 `>= limit` 表示已耗尽，不要求计数大于限额。

SaaS 扫描先于 Redis。仅 Redis 创建/读取/关闭错误被隔离，读取失败停止剩余 API 扫描并返回 redis_unavailable=True，调用方仍可提交已暂存 SaaS 消息。数据库或 create/flush 异常不被吞掉，交给 worker 回滚整个事务。消息、收件箱回执、Delivery Outbox 同 Session 暂存。

## 尚未接入与待确认

- API 耗尽与 SaaS 到期/临近到期已提供可调度 hook，但没有实际启动 worker、连接真实 Redis 或调用 APISIX/Lua 数据面。因此 BE014 此部分是代码与 mock/SQLite 验证完成，真实环境联调与周期调度验收未完成，不能报告全部 done。
- 本次 API hook 针对原生 APISIX Lua 键。兼容 Python 网关使用 `market:gateway:*` 和可能不同的 Redis DB，未覆盖；无法从普通 HTTP 429 推断配额耗尽。
- 总量幂等键使用凭据 ID + 限额；如果运维对同一个凭据、同一总限额主动重置 Redis 总计数，或等待 Lua 一年 TTL 后开启新周期，目前无法区分新的总量周期。需要明确的配额版本/reset epoch 后再扩展键；日/月天然按 UTC 周期隔离。
- Redis 计数可能在周期边界/TTL 清除，worker 必须在有效周期内扫描才能捕获耗尽事实；该方案是轮询通知，不能保证每一个短暂耗尽事件都被观察到。
- SLA 企业通知：当前考核含全局交付样本，即使 profile 有 product_id，交付查询也未按产品/企业过滤。因此仅发给平台角色；企业告警需先明确样本归属与可见范围。
- 清算 service/expert/channel 参与者目前部分明细只有名称、没有 participant_id，不能按名称推断用户或扩大通知范围；当前覆盖可明确定位的订单买卖企业及平台财务人员。
- 既有实名认证审核接口没有 pending 状态校验；重复审核会更新审核时间并形成新的结果事件。既有订单 confirm_payment 分支也没有统一的 expected 状态校验；消息按订单 paid 去重，但本次未修订这些业务权限/状态机规则。
- 新消息依赖约定的 create(category=..., tenant_id=...) 接口。共享目录中的消息中心协作者已提供该接口；本次未修改其实现。
