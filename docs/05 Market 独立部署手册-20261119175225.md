# Market 数据集运营服务管理平台独立部署手册

适用范围为 K8S 本地开发安装，以及使用 Forgejo、Harbor、Flux 的完整离线部署。现场示例采用 K8S1 负责构建、K8S2 负责运行。单集群现场可共用一座 Harbor，省略跨 Harbor 复制。

## 1. 部署拓扑、前置条件与交付清单

~~~text
Forgejo 仓库 main
    → 仓库级 Runner / BuildKit（K8S1，market-ci）
    → 源 Harbor 的 market 项目
    → 目标 Harbor 的 market 项目（K8S2 定时 Pull，可按需立即执行）
    → Flux OCIRepository 按摘要获取发布包
    → market-api → market-workers、market-web → market-jobs
~~~

| 项目 | 示例与要求 |
| --- | --- |
| K8S1 | 节点 192.168.10.10，Forgejo 可达，BuildKit 可访问构建镜像仓库、阿里云 PyPI 和 npm 源 |
| K8S2 | 节点 192.168.10.17，可在无互联网条件下运行，目标 Harbor 能访问源 Harbor |
| Harbor | 源 192.168.10.10:30443，目标 192.168.10.17:30443，HTTPS、私有项目 market |
| 命名空间 | market 为应用，market-registry 为 Harbor，market-ci 为源端 Runner，flux-system 为目标端 Flux |
| 应用访问 | 示例 NodePort 30080 为商城和后台，30082 为 APISIX，30081 为兼容网关。生产对外入口使用实际域名和 HTTPS |
| 节点与工具 | 可调度的 Kubernetes、containerd、可用的动态存储类、kubectl。构建节点还需 Helm、BuildKit 或 nerdctl。部署管理机使用 Bash、Python 3、PyYAML、OpenSSL、curl 和 Flux CLI |
| 已验证组合 | 模拟 K8S2 为 Kubernetes 1.35.8、containerd 2.2.3、linux/amd64。Harbor Chart 1.19.4、Harbor 2.15.4、Flux CLI 2.10.0，两个控制器为 v1.10.1 |
| 持久化 | 示例使用 local-path。应用参考配置共 6 个 PVC，PG 5 GiB、Redis 2 GiB、MinIO 5 GiB、etcd 1 GiB、ClamAV 1 GiB、Redis 维护证据 1 GiB。Harbor 存储另计。客户环境按容量、恢复目标和调度规则选择存储类 |

离线交付应备齐六个应用镜像、同版本 OCI 包、基础组件和 Flux 控制器镜像及锁清单、与发布包提交一致的源码快照、Flux CLI、ClamAV 病毒库和独立校验值。首次搭建目标 Harbor 时，还需提前准备 Chart 包及其全部运行镜像。Robot 凭据、数据库密码、站点密钥、证书私钥和备份通过现场安全渠道交接。

源码以 Forgejo 发布提交为准。开发验证也可从 GitHub 获取同一提交。构建侧使用获准的 Git 凭据克隆仓库，离线运行侧使用后续章节的源码归档。 [Forgejo 仓库](http://8.145.35.173:3000/hxyl/OperationPlatform) · [GitHub 镜像](https://github.com/jameswangjz/market)

每次执行 kubectl 和 Helm 前检查当前上下文。节点需具备可用 DNS、正确时间同步及可访问的存储。对外入口开启前完成密码更换、TLS 配置及端到端验收。

~~~bash
kubectl config current-context
kubectl get nodes -o wide
kubectl get storageclass
python3 -c 'import yaml'
~~~

## 2. 安装前选择数据库

| 模式 | 选择参数 | 库与权限准备 |
| --- | --- | --- |
| 内置 PostgreSQL | 仅指定 --db-type Postgres，或省略全部数据库参数 | Market 使用同命名空间的 market-postgres:5432/market。首次安装初始化账号和库，重复应用原站点配置时应复用原密码及 PVC |
| 指定 PostgreSQL | --db-type Postgres，外加地址、用户名、密码文件 | 提前创建数据库和应用用户。用户名应具有连接、建表、索引、序列及应用 DML 权限。未填端口时为 5432，未填 --db-name 时为 market |
| 指定达梦 | --db-type Dameng，外加地址、用户名、密码文件 | 提前创建专用应用用户及 Schema，按验收使用的权限检查 CREATE SESSION、CREATE TABLE、CREATE SEQUENCE、CREATE INDEX 和 SYS.DBMS_LOCK 调用。未填端口时为 5236，Schema 由登录用户确定 |

地址格式为 HOST[:PORT]，IPv6 使用 [IPv6]:PORT。三个外部连接参数须一起提供。密码文件填写一行原始密码，使用 0600 权限，避免把密码作为命令行字面量。Market 将连接配置保存于 market-db-connection Secret，API、兼容网关、Worker 和 CronJob 引用其 DATABASE_URL。外部库模式的应用部署清单省略内置 PG Deployment、Service 及 PVC。部署选项适用于新站点，已存量数据的换库操作按第 10 节执行。

达梦发布包应声明 database_types 包含 Dameng。API 与兼容网关镜像内含 SQLAlchemy 2.0.36、dmPython 2.6.1 和 dmSQLAlchemy 2.0.17。已实测达梦 V8 rev244896、COMPATIBLE_MODE=0。客户达梦 8.4 的具体补丁构建仍需现场核验。首次启动用单个 API 实例完成初始化，生成的表、索引及可重复启动由测试验收。

## 3. 单集群开发安装

联网开发集群使用仓库安装脚本。该脚本构建本地 containerd 镜像并安装基础开发工作负载，完整发布的 Worker 和定时任务由后续 Flux 路径统一管理。多节点使用本地镜像时，需提前在每个可能调度 Market 的节点导入相同的镜像标签，或采用 Harbor 路径。脚本默认使用 market 命名空间。

~~~bash
# 在仓库根目录运行。该脚本也支持 --help。
bash scripts/deploy.sh --db-type Postgres

# 使用指定 PostgreSQL 时，改用下列命令。
bash scripts/deploy.sh --db-type Postgres \
  --db-address pg.example:5432 --db-user market_app \
  --db-password-file /secure/market-pg.password --db-name market

# 使用指定达梦时，改用下列命令。
bash scripts/deploy.sh --db-type Dameng \
  --db-address dm.example:5236 --db-user MARKET_APP \
  --db-password-file /secure/market-dm.password

kubectl -n market get deploy,pod,pvc,svc
kubectl -n market rollout status deploy/market-api --timeout=180s
kubectl -n market rollout status deploy/market-web --timeout=180s
~~~

三个部署命令任选其一。源码包缺少 Git 元数据时，追加 GIT_SHA 环境变量，填入源码提交的 Git SHA 前缀。镜像标签按 YYYYMMDDHHMMSS-GitSha 生成。如现场已有旧版无持久化 Redis，安装器会提示先完成 Redis 数据备份与 PVC 迁移。

## 4. K8S1 构建与发布

### 4.1 安装源 Harbor

以下安装脚本的站点参数为示例源节点 192.168.10.10、NodePort 30443 和 local-path。客户地址、存储类、节点资源或仓库域名不同，先调整 Helm values、安装脚本与 Runner 注册配置，再执行。证书 SAN 须覆盖客户端使用的 IP 或域名。K8S1 用于发布时，只需部署 Harbor、Runner 与 BuildKit 以及构建和签名库来源所需工具，Market 应用可以部署在目标集群。

~~~bash
helm pull harbor --repo https://helm.goharbor.io --version 1.19.4
bash scripts/install_market_harbor_env1.sh \
  k8s/ci/harbor-env1-values.yaml ./harbor-1.19.4.tgz
helm -n market-registry list
kubectl -n market-registry get pods,pvc
curl -fsS --cacert /root/market/ops/harbor-env1/ca.crt \
  https://192.168.10.10:30443/api/v2.0/health
python3 scripts/bootstrap_market_harbor_project.py
~~~

Harbor 健康接口应返回 healthy。为 market 私有项目配置两个机器人账号，分别用于发布 pull/push 和复制 pull。Harbor 管理凭据和机器人密钥保存在节点受保护目录。已验证的 Helm 参数参见 [Harbor Chart 1.19.4](https://github.com/goharbor/harbor-helm/tree/v1.19.4)。

### 4.2 安装仓库级 Forgejo Runner

在 hxyl/OperationPlatform 的仓库设置中启用 Actions，创建仓库级 Runner，标签为 market-build。安装脚本通过终端接收 UUID 与 Token，并写入 market-ci 内的 Secret。Runner 容器领取任务和检出代码，同 Pod 的 BuildKit 容器构建镜像。

~~~bash
bash scripts/configure_market_forgejo_runner.sh k8s/ci
kubectl -n market-ci rollout status deploy/market-forgejo-runner --timeout=300s
kubectl -n market-ci get pods
kubectl -n market-ci exec deploy/market-forgejo-runner -c runner -- \
  /tools/buildctl --addr tcp://127.0.0.1:1234 debug workers
~~~

Forgejo 仓库 Actions 变量设 HARBOR_REGISTRY=192.168.10.10:30443、HARBOR_PROJECT=market。把发布机器人用户名和密钥分别存为仓库 Secret HARBOR_USERNAME 和 HARBOR_PASSWORD。Runner 应能领取仓库任务。CI 使用仓库 CA 验证 Harbor。

### 4.3 生成完整版本

Forgejo main 上相关源码路径变更会触发 Publish Market images and OCI release。也可在 main 手动分发同一工作流。工作流以一次构建的版本标签分别推送 market-api、market-web、market-gateway、market-mock-api、market-mock-saas、market-redis-maintenance，再推送 market/market-release。应记录版本、完整 Git 提交、OCI 摘要及六个镜像摘要。成功门槛为 CI 报告 OCI release payload re-pulled and verified，工作流状态成功。

~~~text
版本格式  YYYYMMDDHHMMSS-GitSha
应用镜像  market/<组件>:<版本>
发布包    market/market-release:<版本>
发布依据  market/market-release@sha256:<OCI 摘要>
~~~

验证包和镜像摘要绑定由仓库脚本完成，K8S2 部署前再次独立验证。一个版本使用一套构建产物。

| infra/postgres | 16-alpine |
| infra/redis | 7-alpine |
| infra/minio | RELEASE.2024-12-18T13-15-44Z |

| infra/etcd | v3.5.15 |

现有环境从 K8S1 的 /root/market/ops/ci-env1 交接 market-infra-images-lock.json 和 market-flux-images-lock.json。全新环境从可信来源按平台拉取已审核镜像，再将其放入表中的目标路径。第三方镜像示例如下，其他条目按同样流程。Presidio 的现有验证镜像优先从已锁定的原 Harbor 复制或从镜像备份导入，避免根据可变 latest 标签重新选型。

~~~bash
export SOURCE_REGISTRY=192.168.10.10:30443
# 在已配置 Harbor CA 信任的 K8S1 节点执行。
# 登录使用已有项目级机器人和 --password-stdin。
nerdctl -n k8s.io pull --platform linux/amd64 docker.io/library/postgres:16-alpine
nerdctl -n k8s.io tag docker.io/library/postgres:16-alpine \
  "$SOURCE_REGISTRY/market/infra/postgres:16-alpine"
nerdctl -n k8s.io push --platform linux/amd64 \
  "$SOURCE_REGISTRY/market/infra/postgres:16-alpine"
~~~

如须重新制作锁清单，待全部镜像标签推送且平台架构核验后，在仓库根目录执行。配置只读机器人 JSON，格式为 name、secret 两个字段。选用已有锁时保留其来源、平台及摘要字段。

~~~bash
export SOURCE_REGISTRY=192.168.10.10:30443
export SOURCE_READ_AUTH=/secure/source-harbor-robot.json
export SOURCE_CA=/secure/source-harbor-ca.crt
PYTHONPATH=scripts python3 -B - <<'PY'
import json
import os
from pathlib import Path
from verify_market_release import Registry

host = os.environ["SOURCE_REGISTRY"]
client = Registry(host, Path(os.environ["SOURCE_READ_AUTH"]), Path(os.environ["SOURCE_CA"]))
groups = {
    "infra": {
        "postgres": "16-alpine", "redis": "7-alpine",
        "minio": "RELEASE.2024-12-18T13-15-44Z", "apisix": "3.19.0-debian",
        "etcd": "v3.5.15", "clamav": "1.4",
        "presidio-analyzer": "sha256-ae8f6f111ac2", "prometheus": "v2.54.1",
        "alertmanager": "v0.27.0", "mailpit": "v1.21.8",
    },
    "flux": {"source-controller": "v1.10.1", "kustomize-controller": "v1.10.1"},
}
for group, names in groups.items():
    locked = []
    for image, tag in names.items():
        repo = f"market/{group}/{image}"
        digest = client.digest(repo, tag)
        if client.digest(repo, digest) != digest:
            raise SystemExit(f"Digest mismatch: {repo}")
        locked.append({"reference": f"{host}/{repo}:{tag}", "digest": digest})
    Path(f"market-{group}-images-lock.json").write_text(json.dumps(locked, indent=2) + "\n")
    print(group, len(locked), "verified")
PY
~~~

## 5. K8S2 Harbor 复制与节点信任

### 5.1 安装目标 Harbor 并完成复制

已有目标 Harbor 可直接配置复制。新建目标 Harbor 前，在联网侧按选定的 Helm values 执行 helm template，备齐 Chart 和渲染结果引用的镜像。将镜像预导入所有调度 Harbor 的节点，或者改为现场已有的内网镜像仓库。目标 Harbor 的证书 SAN 须覆盖访问地址。

在 K8S2 上执行。该示例使用仓库的 k8s/ci/harbor-env1-values.yaml 作为基础 values。证书、私钥、管理密码及源 CA 已由现场安全渠道交付。

~~~bash
kubectl config current-context
kubectl create namespace market-registry --dry-run=client -o yaml | kubectl apply -f -
kubectl -n market-registry create secret tls harbor-env2-tls \
  --cert=/secure/harbor-env2.crt --key=/secure/harbor-env2.key
kubectl -n market-registry create secret generic harbor-env2-admin \
  --from-file=HARBOR_ADMIN_PASSWORD=/secure/harbor-env2-admin.password
kubectl -n market-registry create secret generic harbor-source-ca \
  --from-file=ca.crt=/secure/source-harbor-ca.crt
helm upgrade --install harbor ./harbor-1.19.4.tgz -n market-registry \
  -f ./harbor-env1-values.yaml \
  --set-string externalURL=https://192.168.10.17:30443 \
  --set-string expose.tls.secret.secretName=harbor-env2-tls \
  --set-string existingSecretAdminPassword=harbor-env2-admin \
  --set-string caBundleSecretName=harbor-source-ca \
  --wait --timeout 10m
curl -fsS --cacert /secure/target-harbor-ca.crt \
  https://192.168.10.17:30443/api/v2.0/health
~~~

上述创建 Secret 操作用于首次安装。升级复用站点现有的凭据和证书。Harbor 的 CA Bundle 使用 ca.crt 键验证源仓库。 [Helm Chart 配置参数](https://raw.githubusercontent.com/goharbor/harbor-helm/v1.19.4/values.yaml)

在目标 Harbor 创建私有项目 market。在管理界面创建源仓库端点，类型为 Harbor，地址为源 Harbor HTTPS，使用源端复制只读机器人，保持证书校验并测试连接。新增 Pull 规则，仓库匹配 market/**，保留命名空间层级，覆盖容器镜像和 OCI 制品。可按 10 分钟周期执行，首次可手动执行。完成后核对 OCI 摘要与源端一致、六个应用镜像到齐、infra 和 flux 子路径保留。另创建目标 Harbor 的项目级只读机器人供 K8S2 拉取。 [Harbor 复制规则文档](https://goharbor.io/docs/2.15.0/administration/configuring-replication/create-replication-rules/)

### 5.2 配置 containerd 信任及 Secret

在所有可能调度应用和 Flux 的节点配置目标 Harbor CA。下例采用 /etc/containerd/certs.d，先确认有效 config_path。集群尚未启用该目录时，按 containerd 版本修改对应 CRI registry 配置并逐节点验证。

~~~bash
export TARGET_REGISTRY=192.168.10.17:30443
export TARGET_CA=/secure/target-harbor-ca.crt
containerd config dump | grep -E 'registry|config_path'
dir="/etc/containerd/certs.d/$TARGET_REGISTRY"
install -d -m 0755 "$dir"
install -m 0644 "$TARGET_CA" "$dir/ca.crt"
cat > "$dir/hosts.toml" <<EOF
server = "https://$TARGET_REGISTRY"
[host."https://$TARGET_REGISTRY"]
  capabilities = ["pull", "resolve"]
  ca = "ca.crt"
EOF
~~~

下面在 K8S2 管理目录执行。机器人文件采用 Harbor 导出的 name、secret 两字段。OCIRepository 单独引用 CA Secret。 [containerd hosts.toml 配置](https://github.com/containerd/containerd/blob/main/docs/hosts.md)

~~~bash
umask 077
export SITE=/root/market/ops/market-env2
export TARGET_REGISTRY=192.168.10.17:30443
export TARGET_CA=/secure/target-harbor-ca.crt
export TARGET_READ_AUTH=/secure/target-harbor-robot.json
export DOCKER_CONFIG="$SITE/docker"
export SSL_CERT_FILE="$TARGET_CA"
install -d -m 0700 "$DOCKER_CONFIG"
cd "$SITE"
python3 - <<'PY'
import base64
import json
import os
from pathlib import Path

robot = json.loads(Path(os.environ["TARGET_READ_AUTH"]).read_text())
auth = base64.b64encode(f"{robot['name']}:{robot['secret']}".encode()).decode()
config = {"auths": {os.environ["TARGET_REGISTRY"]: {"auth": auth}}}
(Path(os.environ["DOCKER_CONFIG"]) / "config.json").write_text(json.dumps(config))
PY
for ns in market flux-system; do
  kubectl create namespace "$ns" --dry-run=client -o yaml | kubectl apply -f -
  kubectl -n "$ns" create secret generic market-harbor-pull \
    --type=kubernetes.io/dockerconfigjson \
    --from-file=.dockerconfigjson="$DOCKER_CONFIG/config.json" \
    --dry-run=client -o yaml | kubectl apply --server-side -f -
done
kubectl -n flux-system create secret generic market-harbor-ca \
  --from-file=ca.crt="$TARGET_CA" --dry-run=client -o yaml | kubectl apply --server-side -f -
~~~

## 6. 核验发布包并安装 Flux

在能访问 Forgejo Git 对象的管理机上，从成功发布的任务取完整提交。把归档和校验文件送到 K8S2。各版本的归档及渲染结果存入独立目录。

~~~bash
read -r -p '输入发布日志记录的完整 Git 提交: ' RELEASE_COMMIT
git cat-file -e "$RELEASE_COMMIT^{commit}"
git archive -o market-deployment-source.tar "$RELEASE_COMMIT" \
  k8s scripts/market_database.py scripts/render_market_env2.py \
  scripts/verify_market_release.py scripts/market_release_bundle.py
sha256sum market-deployment-source.tar > market-deployment-source.tar.sha256
~~~

在 K8S2 准备同版本源码归档及校验、两份锁清单和 Flux CLI。下面使用第 5 节的环境变量。首次安装以站点目录作为 WORK。升级每个候选版本另建 WORK 并复用原站点凭据。

~~~bash
export WORK="$SITE"
cd "$WORK"
sha256sum -c market-deployment-source.tar.sha256
mkdir -p source release
tar -xf market-deployment-source.tar -C source
read -r -p '输入发布包 OCI 摘要（sha256:...）: ' OCI_DIGEST
export OCI_DIGEST
"$SITE/flux-2.10.0" version --client
"$SITE/flux-2.10.0" pull artifact \
  "oci://$TARGET_REGISTRY/market/market-release@$OCI_DIGEST" --output release
python3 -B source/scripts/verify_market_release.py --bundle release \
  --registry "$TARGET_REGISTRY" --project market --auth-file "$TARGET_READ_AUTH" --ca "$SSL_CERT_FILE"
python3 -B -c 'import json; x=json.load(open("release/release.json")); print(x["version"], x["commit"], x.get("database_types", ["Postgres"]))'
~~~

核对 status=ready、verified_images=6，发布包 commit 与源码归档记录一致。逐项核对目标 Harbor 的基础及 Flux 镜像摘要。达梦站点还需确认发布包声明支持 Dameng。基础锁的源地址采用示例时可直接使用。源地址与示例不同时，将供站点渲染使用的 infra 锁内 reference 的仓库主机改为已经核对的目标 Harbor，保留 market/infra/组件:标签和摘要。

在目标 Harbor 上按标签与摘要核验两份锁。输出应分别为 10 和 2 项。

~~~bash
PYTHONPATH=source/scripts python3 -B - <<'PY_LOCKS'
import json
import os
from pathlib import Path
from verify_market_release import Registry

client = Registry(os.environ["TARGET_REGISTRY"], Path(os.environ["TARGET_READ_AUTH"]),
                  Path(os.environ["SSL_CERT_FILE"]))
for group in ("infra", "flux"):
    images = json.loads(Path(f"market-{group}-images-lock.json").read_text())
    for item in images:
        repository, tag = item["reference"].split("/", 1)[1].rsplit(":", 1)
        expected = item["digest"]
        if client.digest(repository, tag) != expected or client.digest(repository, expected) != expected:
            raise SystemExit(f"Mirrored artifact mismatch: {repository}:{tag}")
    print(group, len(images), "verified")
PY_LOCKS
~~~

### 7.1 离线导入 ClamAV 病毒库

从联网或接入更新源的 ClamAV 实例导出 /var/lib/clamav 下的 main、daily、bytecode 三份签名文件。病毒库随 PVC 独立更新。通过可信渠道将压缩包和校验文件送至 K8S2。

~~~bash
# 在源集群上下文执行。
kubectl -n market exec deploy/market-clamav -- clamd --version
kubectl -n market exec deploy/market-clamav -- sh -ec '
  cd /var/lib/clamav
  set --
  for type in main daily bytecode; do
    for ext in cld cvd; do
      if test -s "$type.$ext"; then set -- "$@" "$type.$ext"; break; fi
    done
  done
  test "$#" -eq 3
  tar -czf - "$@"
' > clamav-db.tar.gz
sha256sum clamav-db.tar.gz > clamav-db.tar.gz.sha256
tar -tzf clamav-db.tar.gz
~~~

首次渲染时 market-clamav 为零副本。后续更新应先停用相关扫描入口，在维护窗口缩容 ClamAV，确认原 Pod 退出并保留原库备份。以下在 K8S2 使用 clamav-image.txt 固定的镜像导入。

~~~bash

cd "$WORK"
sha256sum -c clamav-db.tar.gz.sha256
test "$(tar -tzf clamav-db.tar.gz | wc -l)" -eq 3
for family in main daily bytecode; do
  tar -tzf clamav-db.tar.gz | grep -Ex "$family\.(cvd|cld)"
done
test "$(kubectl -n market get deploy market-clamav -o jsonpath='{.spec.replicas}')" = 0
importer="market-clamav-import-$(date +%H%M%S)"
image=$(cat clamav-image.txt)
(
  trap 'kubectl -n market delete pod "$importer" --ignore-not-found --timeout=90s' EXIT
  kubectl -n market create -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: $importer
spec:
  restartPolicy: Never
  automountServiceAccountToken: false
  imagePullSecrets:
  - name: market-harbor-pull
  containers:
  - name: importer
    image: $image
    command: ["/bin/sh", "-c", "sleep 900"]
    securityContext:
      runAsUser: 0
    volumeMounts:
    - name: signatures
      mountPath: /var/lib/clamav
  volumes:
  - name: signatures
    persistentVolumeClaim:
      claimName: market-clamav-data
EOF
  kubectl -n market wait --for=condition=Ready "pod/$importer" --timeout=240s
  kubectl -n market exec -i "$importer" -- sh -ec '
    cd /var/lib/clamav
    tmp=$(mktemp -d .import.XXXXXX)
    tar -xzf - -C "$tmp"
    for path in "$tmp"/*; do
      test -f "$path"
      test ! -L "$path"
      test -s "$path"
      sigtool --info "$path" | grep -E "^(Version|Signatures):"
      chown 100:101 "$path"
      chmod 0644 "$path"
    done
    cd "$tmp"
    sha256sum ./*
    cd ..
    for path in "$tmp"/*; do
      file=$(basename "$path")
      mv "$path" "$file"
      case "$file" in
        *.cvd) counterpart=$(basename "$file" .cvd).cld ;;
        *.cld) counterpart=$(basename "$file" .cld).cvd ;;
      esac
      if test -f "$counterpart"; then unlink "$counterpart"; fi
    done
    rmdir "$tmp"
  ' < clamav-db.tar.gz
)
kubectl -n market scale deploy/market-clamav --replicas=1
kubectl -n market rollout status deploy/market-clamav --timeout=330s
kubectl -n market exec deploy/market-clamav -- sh -ec 'clamd --version; clamdscan --ping 5'
~~~

## 10. 升级、回退及运维

### 10.1 同数据库升级

1. 记录当前生效的 OCI 摘要以及四个阶段的镜像摘要，保存旧版 market-flux.yaml、foundation.yaml 和站点凭据。数据库、对象存储、Redis 和 etcd 按恢复目标分别备份。数据库变更前在隔离副本核对可恢复性。先备份再变更。

### 10.2 版本回退与换库

保持旧版 OCI 包和全部已引用的镜像。在确认新旧 Schema 可兼容后，重新应用保留的旧版完整 market-flux.yaml，并按相同顺序协调四个阶段。旧 OCI 摘要和旧镜像映射需一并恢复。若结构、数据已变更且旧程序不能读取，应先停止写入，完成隔离恢复验证，再按现场批准的恢复方案切换。镜像回退与数据库恢复是两项操作。

从 PostgreSQL 换为达梦或反向切换，需另行迁移数据，校验表、约束、记录数、关键金额、审计、对象关联、写入及恢复能力。先进行隔离迁移和验收，再安排停写窗口，切换所有数据库客户端及定时任务，变更后复核。现有客户数据迁移及对账范围在上线变更中明确。

### 10.3 Redis 计划维护

管理端在「系统设置 → 系统维护」依次执行「Redis维护准备」与「Redis维护后恢复」，分别用于停机前备份和计费分代封存，以及重启后的连续性验证与恢复。非计划重启先刷新状态，证据能证明连续性时继续既有分代，存在无法证明的缺口时经审核执行「Redis异常重启恢复」并保留缺口和旧游标。达梦先由数据库管理员完成独立备份及恢复验证。

仓库中的 stop-market.sh 与 start-market.sh 适用于依赖同命名空间内置 PostgreSQL 且已配置相应维护服务的安装。先用 --dry-run 查看计划。Flux 管理的环境还需先暂停会恢复副本的对应 Kustomization，并按现场窗口管理恢复次序。外部库模式按经过验收的现场停启方案执行。
