# Redis持久化与计费来源分代详细设计

生成时间：2026-10-16 13:24:23（北京时间）。用户已确认采用“Redis持久化＋计费来源分代＋缺口审计”。

## 1. 目标与不变量

- 保留 PostgreSQL 原计费事实、旧采集游标、订单经济快照和受保护订单，不清空 Redis 共享数据，不补造调用。
- 新代次恢复后续采集，不代表丢失的历史计费流已恢复。跨缺口订单继续人工核定；不得按零用量自动退款。
- 稳定来源 ID 与 Redis 每次启动的 process run_id 分离；来源 ID 为 40 位十六进制，兼容现有回执字段。
- 同一来源内重放不重复入账；不同来源即使有相同 Redis 事件 ID 也不覆盖旧事实。

## 2. 持久化部署

market 命名空间内新增 `market-redis-data` PVC，local-path、ReadWriteOnce、10Gi；Redis 单副本、Recreate，使用现有 Redis 7 镜像，不在本次升级 Redis 大版本。

配置：`appendonly yes`、`appendfsync everysec`、`dir /data`、低频 RDB 快照、`noeviction`、持久化失败保护。持久卷防止普通容器重建丢数据；单机 local-path 不代表跨节点高可用或磁盘损坏容灾。

已有数据迁移不能直接让空 PVC 启动：先准备挂载 PVC 的临时容器，在短维护窗口暂停旧 Redis 写入、SAVE、备份并校验 RDB；将备份写入 PVC。新 Redis 首次用 `--appendonly no` 在临时端口启动，验证 RDB 内容，开启 AOF 并等待首次重写成功，再恢复正式配置启动。否则直接用 AOF 模式启动可能忽略仅有的 RDB 文件。

备份仅在开发主机权限受限目录保存，不提交 Git。迁移失败不自动清空或覆盖 PVC；保留失败阶段、备份与回退依据。基础 deploy.sh 对现有无 PVC 的 Redis 提前拒绝盲目替换。

## 3. 来源与缺口模型

| 对象 | 内容 |
| --- | --- |
| SourceGeneration | 稳定 ID、独立 stream、状态、绑定的进程 run_id、生效边界、旧来源/游标、封存哈希及操作历史 |
| SourceGap | 新来源关联、旧可信来源与水位、发现/切换时间、操作人和理由；未知缺失数量不填写为零 |
| Cursor | 沿用现有表，按实际 stream 分开保存；旧 `charges:v1` 游标保留，新来源从自己的空流起步 |
| Charge | 保留原事实；新事实以来源＋原事件 ID 形成稳定身份，另存真实 event_id，避免跨代次 ID 冲突 |

新流命名：`market:apisix:charges:v1:<source_id>`。兼容保留来源 hash 中的 run_id 字段，但受管理来源的该字段表示稳定来源 ID；process_run_id 才是当前 Redis 启动 ID。明确记录 stream、ready/paused 和 not_before_us。

来源开通分两步：先持久化 pending 来源、缺口和独立游标，再通过 Redis CAS 发布，最后确认 active。中途失败保持安全拦截；重试复用 pending 记录，不复制缺口或移动旧游标。

## 4. 网关、退款与升降级

网关先读取来源，Lua 原子扣额时再次核对来源、stream、ready 状态和策略快照。来源暂停或变化时不扣额度、不写错误来源的事件。拒绝把生效边界之前的当前订阅周期按全新额度继续提供，避免因丢失旧计数而重置额度。

新开通且起始日在边界之后的周期可使用新来源；跨缺口旧周期需人工核定，不在本次自动补额。已知旧账本仍保留，不将新流的零条事件解释为旧周期零消费。

退款试算、执行、跨版本切换回执统一通过 source_context 选择来源和游标。财务来源 ID 与执行期间检测 Redis 进程是否变化的 run_id 分开处理，保留原有 TOCTOU 防护。回执不跨缺口自动升级为可信。

## 5. 重启恢复

计划重启：暂停来源接入，排空已接受事件，封存金融流、月/日计数、覆盖基线及来源标记的证据。重启后必须证据相同才重新绑定物理进程并恢复该代次。每日键自然过期等不能证明一致的情况保守拒绝，不猜测用量。

非计划重启：没有可信封存证据时保持拦截；由显式运维操作判定恢复或新开缺口代次。不能只比较 run_id 后覆盖数据库，也不能通过重启采集进程跳过校验。

AOF everysec 仍存在短暂数据丢失窗口，本次不承诺银行级零丢失。PostgreSQL 长期保存已采集财务事实；来源与用量完整性门禁继续生效。
