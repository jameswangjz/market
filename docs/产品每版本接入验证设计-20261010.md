# TRD-BE-003 每版本接入验证设计与集成契约

日期：2026-10-10。交付范围仅新增 `backend/app/version_gateway.py`、`backend/tests/test_version_gateway.py` 和本文档；不修改 main/storefront/trading_policy，不提交、不部署。

## 本次可执行子集与现状

模块提供 `install(ns)`，将一个新 SQLAlchemy 模型注册到传入的 `Base.metadata`，返回 hooks，不注册 HTTP 路由、不建表、不提交事务、不执行原始网络请求。支持 `ProductReleaseVersion` 的 API/model API 交付版本配置、四审后的 pending_integration、健康验证、现有 APISIX 发布证据绑定和发布/购买门禁。

现有 `ApiGatewayRoute.product_id` 唯一；`api_order_context`、兼容网关、凭据配置仍按产品定位路由。当前只能验证与现有产品路由完整一致的一个版本。其他版本可以保存独立配置，但验证返回 409，不覆盖原路由。已有 active 路由只健康验证并采纳最新匹配的发布记录，不重新 PUT APISIX；有已支付金额的产品且路由非 active 时拒绝重新发布。模块从不修改 route_key、上游、认证或版本标识，不为 v2 复用 v1 的证据。

真实 APISIX 未验证；主应用尚未挂接本模块。TRD-BE-003 全任务仍有集成与多版本路由改造余项。

## 现有逻辑研读结论

- main 的四审链为 pending_review → quality_review → security_review → operation_review，运营批准目前直接设 published，再生成 OAuth 客户端及自动发布产品路由。集成时必须在最终批准分支改变状态，并替换该分支自动发布调用。
- `GatewayConfigBody` 已有限制 timeout、health method、auth/scope 和配额的参数校验；模块复用它，另限制版本绑定、route_key 与健康路径形态。
- `gateway_auto_publish` 使用原始 `httpx.Client` 发健康请求，关闭重定向但没有 DNS/IP 私网/白名单检查。`validate_gateway_config` 只检查 URL 和配置形态，不能当作 SSRF 校验。
- `publish_apisix_route` 生成 revision、publish record，调用现有 Admin API，失败保留 failed 记录；APISIX 关闭时直接返回 True。模块复用该发布函数并强制 APISIX 开启与真实持久化发布记录存在，避免将禁用模式当作成功。
- storefront 当前按产品路由健康提示及最新 APISIX revision/record 过滤，仅开放与 route.version 相等的版本。接入后还须检查本模块版本证据，保留价格、Logo、SaaS 和文件原有检查。
- 仓库当前没有 `validated_http_request` 或可复用 SSRF 白名单实现。需求文档中的 SSRF 要求尚未落地，不能用原始 httpx 替代。

## 新模型与证据

`version_gateway_configs` 每 release version 一行，外键关联产品、release version、已有 route、revision、publish record；version_id 唯一。字段保存上游、route_key、version_code、auth_mode、upstream_auth_mode/scope、timeout_ms、strip_prefix、health_method/path、配置配额。验证字段包括 status、healthy、health_status_code、verified_at/by、evidence_hash、revision_id、publish_record_id、error_code。

不在新表复制客户端秘密，不输出响应正文或异常 URL；哈希包含客户端身份/秘密、配置、版本配额、产品与版本身份、route ID 和实际 APISIX payload。验证时间表示健康请求时间，APISIX record.completed_at 表示发布完成时间。active 路由采纳的是此前的发布记录，不能称为本次重新发布或数据面验证。

健康 2xx 只说明健康端点可达，不证明业务请求的 OAuth/scope、配额或 APISIX 数据面行为。healthy 可为 True 而 status 为 failed，例如健康成功后发布失败；门禁必须同时检查 verified 状态及匹配发布证据。

配置更新会清空验证字段，已售版本配置更改返回 409。相同配置重复保存保留证据。四审完成 hook 将该产品配置全部失效，进入新的验证周期。最新 revision 失败、最新 publish record 失败、payload 漂移、凭据轮换、配额漂移、版本停用或路由停用都会使 ready 返回 False。没有证据过期时长策略，持续健康监测另行集成。

## Hooks 与事务契约

| Hook | 参数与用途 |
| --- | --- |
| requires_integration | `(product)`：api/model_api/tenant_access 返回 True |
| on_review_complete | `(db, product, user)`：仅运营批准时调用，原状态必须 operation_review；校验运营审核角色；需要接入则 pending_integration，其他 published |
| save_config | `(db, product, version_id, body, user)`：body 为 GatewayConfigBody 或 dict；使用已有 gateway_operator_allowed；仅 API/model API，校验版本归属和已售保护 |
| verify_version | `(db, product, version_id, user)`：仅 pending_integration/published，版本 active；安全 HTTP 健康验证，然后复用 publish_apisix_route 或采纳 active 路由证据；返回 ORM config，由调用方判断 status |
| version_ready | `(db, product, version)`：只读证据门禁，不负责四审和定价 |
| require_ready | `(db, product, version_id=None)`：无 version_id 要求全部 active release versions 就绪；指定 ID 只校验所购版本，未就绪 409 |
| public_versions | `(db, product)`：仅 published，过滤有效价格及证据，返回公开字段 id/version_code/description/price；API 分支使用 |

调用方拥有 commit/rollback。配置保存、验证、审核 hook 对 Product 加行锁，配置和路由验证亦加行锁；PostgreSQL 可用于同产品操作串行化，SQLite 测试不验证行锁。其他配置/订单入口也必须遵守同产品锁，否则不能保证并发保护。

验证返回 failed 时，调用方先提交以保留错误和现有 APISIX 发布失败记录，再返回 409。参数、权限、缺适配器和路由不匹配异常在网络调用前抛出。APISIX PUT 与数据库提交没有分布式事务；若提交失败，应保持数据库门禁关闭并进行运维对账。模块不会删除外部路由来模拟回滚，防止损害已售请求。

## main 挂接片段

以下是供主 agent 修改的调用位置，本文没有执行这些集成修改。

安装必须在模型定义完成后、第一次 metadata.create_all/启动建表之前：

```python
from .version_gateway import install as install_version_gateway
version_gateway = install_version_gateway(globals())
```

安全 HTTP 注入契约：`validated_http_request(method, absolute_url, *, timeout, follow_redirects=False)` 返回带 `status_code` 的响应，拒绝抛 `ValueError`/`RuntimeError`/`httpx.HTTPError`。这是服务端可信依赖，不能从请求参数传入，也不能直接指定 httpx.request。现有实现缺失时，保留未配置状态，verify 返回 503。

该安全封装须对实际完整健康 URL 校验 scheme、凭据、DNS 的全部解析地址和连接目标；私网/Kubernetes 服务仅允许通过现有环境明确批准的主机/IP/端口白名单。必须防 DNS rebinding、IPv4/IPv6/映射地址绕过，禁止重定向并落实连接目标校验；不能仅判断 URL 字符串或用“私网部署”豁免。健康和实际发布的上游地址均须纳入白名单，APISIX Admin 地址是独立可信运维配置。由主 agent 接入经过验证的安全网络层，本模块不自行实现网络安全。

运营审核分支应在设 published 之前调用：

```python
elif stage == "operation":
    product.status = version_gateway["on_review_complete"](db, product, user)
# 保留审核意见、审核日志、通知、ensure_oauth_client 等现有流程。
# 该批准分支的 gateway_auto_publish 改由专用验证入口触发。
# API pending_integration 通知和文案也由主 agent 调整。
```

为版本配置与验证注册独立入口，保留认证依赖：

```python
@app.put("/api/products/{product_id}/versions/{version_id}/gateway-config")
def save_version_gateway(product_id: str, version_id: str, body: GatewayConfigBody,
                         user: User = Depends(current_user), db: Session = Depends(db_session)):
    product = gateway_product(product_id, db)
    config = version_gateway["save_config"](db, product, version_id, body, user)
    db.commit()
    return {"version_id": config.version_id, "status": config.status}

@app.post("/api/products/{product_id}/versions/{version_id}/verify-integration")
def verify_version_gateway(product_id: str, version_id: str,
                           user: User = Depends(current_user), db: Session = Depends(db_session)):
    product = gateway_product(product_id, db)
    config = version_gateway["verify_version"](db, product, version_id, user)
    db.commit()
    if config.status != "verified":
        raise HTTPException(409, "Version integration failed")
    return {"version_id": config.version_id, "status": config.status,
            "healthy": config.healthy, "verified_at": config.verified_at}
```

最终产品发布必须限平台发布权限、加同产品行锁、确认状态 pending_integration，才执行：

```python
version_gateway["require_ready"](db, product)
product.status = "published"
audit(db, actor, "publish_integrated_product", "product", product.id)
db.commit()
```

旧 `/publish`、gateway-config/publish、health-check、rollback、配置保存入口均需审查并改用门禁或关闭绕过；不能因为存在新入口而保留旧审核分支自动发布。订单入口检查 product.status == published 后，以订单选定 product_version_id 调 `require_ready(db, product, product_version_id)`，并保留购买资格、价格和交易策略检查。

## 迁移方案

1. 主 agent 在启动建表前安装模块，使新模型进入同一 Base.metadata。生产迁移在现有表都已存在时，只创建新表：

   ```python
   with engine.begin() as connection:
       version_gateway["Config"].__table__.create(connection, checkfirst=True)
   ```

2. 本次不修改已有表、唯一约束、route_key、消费者、订单关联和路由流量。旧数据不自动标记 verified。允许显式按当前 route 字段创建其匹配版本配置，随后通过安全封装健康验证并采纳最新匹配 APISIX 记录。没有 APISIX 记录的 active 路由拒绝采纳，由运维人工对账和授权重发流程处理。
3. 上线门禁会隐藏没有新证据的旧产品。由主 agent 决定分批启用和存量验证顺序，先准备安全封装与证据，不通过伪造 healthy/verified 进行兼容。
4. 新外键没有级联删除。版本删除需要显式清理未售配置；已售版本继续禁止删除，删除失败不会默默遗失证据。回滚模块集成可保留新表；不得删除原路由。
5. 多版本路由后续需新增 nullable release_version_id，回填旧路由指向匹配版本，经审查将 product_id 唯一约束替换为版本唯一约束。已售旧 route ID/key 必须保持；v2 创建新 ID/key。订单/凭据/兼容网关按版本或 route ID 定位，OAuth、限流和健康证据同步调整，验证 APISIX 路由互不覆盖后再开放多版本。此项超出本任务三文件范围。

SaaS 的 SaaSProductVersion 与 ProductReleaseVersion 属于不同表，本模型不伪装支持 SaaS。tenant_access 四审后可 pending_integration，但 ready 关闭；需单独实现 SaaS 操作接口/OAuth 接入验证后再启用相应发布流程。文件与线下发布仍由原交易策略验证。
