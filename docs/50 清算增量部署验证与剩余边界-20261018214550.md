## 4. 部署过程发现及修复

- PostgreSQL原存活探针仅1秒。节点高负载时探针失败触发数据库重启，首次备份被中断，部署门禁因此停止，未将该次尝试当作发布成功。
- 已重新取得约3.2MB备份并校验备份目录；PostgreSQL采用Recreate，避免两个实例同时使用同一数据卷，探针改为5秒、存活连续失败阈值6次。
- API健康接口改为异步无阻塞接口，避免共用业务线程池；API探针同样保留有限容忍时间。
- SLA采集采用事务内锁等待2秒、语句10秒限制；超时/死锁回滚后返回503并要求重试。再增加最多4个并发采集的准入门禁，超载不进入数据库，不占满业务线程池。
- 生产端仍仅收到200才确认批次；503不删除队列、不重置游标、不伪造采集成功。
- Web滚动切换的短暂TCP重置曾触发旧脚本回退；部署健康门禁改为限时重试包括连接重置在内的错误，未取消失败门禁。
- 三类任务巡检错峰后仍每10分钟一次；应用健康和在线SLA采集错峰后仍每5分钟一次。

首次健康接口通过但财务报表45秒超时没有被判为成功。最终并发门禁部署后，该报表及其余8组接口均通过；实际运行源码与最终清单重新核验。
