# R3多资金来源退款设计补充

## 已确认规则

适用于已升降级的订阅再次发起普通退款。优先退最近到账的升级补款，再退较早到账的支付；每个来源按原支付渠道退款。每笔可用金额为实付减去已完成退款及其他在途冻结金额，不能跨企业、跨币种或超出来源余额。金额精确到分，不用浮点数分配。

退款资金排序与收入成本冲回是两个不同维度。收入、成本及五方分成仍使用退款涉及的原经济段快照；不因优先退升级补款，就把全部退款按最新版本利润或规则计算。

## 服务端关联与边界

1. 由原订单、其有效订阅段、已完成版本变更及VersionChangeFund关联到已确认Payment。来源清单不能由前端任意提交。
2. 未完成、失败补偿或被作废的版本变更不能提供可退款资金。已完成降级退款须扣除，不因本次普通退款重复返还。
3. 来源排序以实际到账时间降序；时间相同按稳定payment_id排序，保证重试一致。付款时间缺失不得猜测先后。
4. 一个退款申请需关联多条支付来源分配记录，不能把原Refund.payment_id单一字段冒充全部原路退款计划；保留该字段的历史兼容语义。
5. 审核冻结时校验并冻结每笔资金来源和金额；金额合计必须等于批准金额。资金不足整体拒绝，不暗中截断用户申请。
6. 执行时逐来源幂等台账，只有资源回收与全部资金步骤完成，才能标记整个退款完成。模拟退款不能标为已验证银行到账。

## 开发边界

BE-011先实现纯资金分配器和严格输入校验，再接入服务端资金关联、来源占用与跨经济段快照。纯函数不负责身份鉴权、DB锁、资源回收或利润计算；不能把纯函数通过当作整个多来源功能完成。

BE-012在已冻结方案上执行，处理并发变化、资金/资源失败、重试和重启恢复。FE-008显示申请/分配/执行结果，不暴露敏感支付或提供方凭证。QA-005验证多来源累计不超退、在途占用、幂等及故障恢复；退款完成后才交由BE-013产生清算负向调整。

## 依赖顺序

按用户最新确认：BE-011完成后启动BE-012，随后收尾FE-008与QA-005。已完成的BE-010保留待验收，不倒退为待开发，也不代用户验收。

## 跨版本经济段核算确认

用户已确认按经济段分别核算：版本变更前已经消费的部分不追溯；变更后以资源切换时冻结的剩余收入、剩余成本、清算规则及可用额度为新段基准，仅计入切换后的实际扣额。普通未变更版本订单仍以月额度乘购买月数为分母。不把新版本月价直接代替旧订单成交快照，也不把同一条历史扣额同时记入新旧两段。

实现必须包括：

1. 新段来源必须关联已验证的版本变更及原订单/订阅段，不能由前端提交或从当前产品价格倒推。
2. 记录资源实际切换边界及计量水位。报价时间、支付时间和实际资源切换时间不能混为一谈；缺少可信切换边界和额度快照的历史变更转人工，不推测零用量。
3. 切换前后的网关策略读取与实际扣额需要一致性保护，防止请求读取旧策略后在切换完成才扣额而归错段。
4. 按新段冻结的剩余额度与切换后实际扣额计算未消费价值，累计退款与在途占用均需扣除。SaaS和不限额API继续使用对应经济段的自然时长及尾部权益回收。
5. 各退款经济腿保存收入、成本与规则快照；资金腿按最近补款优先分配。两者金额需勾稽，但不能把资金来源的排序变为分账规则。
6. 新旧段归属、并发切换、退款占用和资金分配必须在服务端验证。未完成这部分事务接线前，纯分配器通过测试不代表跨版本退款可执行。

当前已有原始/未来未修订段规划和纯资金分配器；以上跨版本事务及计量边界仍为BE-011未完成项，不能提前标记全任务通过。

## BE-011本轮实施边界

### 可信切换边界

网关在同一Redis EVAL内比对本次请求读取的凭据状态、模式、组合及完整周期策略。发生切换、禁用或删除后，旧策略请求必须在扣额和写入账本前失败，不自动按旧参数放行。

切换回执应在同一Redis原子操作中保存来源epoch、扣额流最后ID、Redis时间、各订阅月已用量及目标版本剩余额度，再更新凭据策略。回执按变更ID、方向和凭据身份幂等；已完整切换的重试返回原边界，不能重新取时间或用量。若保存回执后策略写入失败，回执仅代表意图，禁止自动复用旧水位补写策略，须人工核对。补偿方向使用独立回执，不能覆盖首次切换证据。读取旧策略、策略写入及扣额必须具有明确的先后关系。

回执不修改任何用量计数。缺少连续来源、零基线或可信历史时拒绝自动核算，转人工核定；有限额度为零代表没有可回收额度，不能解释成不限额。不限额应使用独立的空值语义，并按时长核算。

### 经济段规划

新经济段冻结收入、成本、清算规则、可用额度及生效起止。有限额API只以切换时可用额度为分母；不限额API与SaaS以本段实际起止时长为分母。切换前的用量不传入新段。每次退款同时生成累计收入冲回、累计成本冲回及本次差额，避免分次舍入重复扣成本。权益按累计金额比例回收，最后一笔处理整数额度或时长尾差。

### 事务接入验收门槛

1. 回执与已验证变更、订单、期限和目标账本唯一关联，并持久化不可变经济段及证据哈希。
2. 读取逐次扣额事实时以切换水位划分，先核对来源连续性和数据库追平情况，再统计本段用量；不能只按应用服务器时间截断。
3. 退款审批在同一事务内校验经济段、在途占用和各支付来源余额，保存多资金腿及多经济腿；并发审批不得超额。
4. 前述持久化及接线通过前，新增纯规划函数或Redis原语均不得被描述为完整API退款已可执行。执行、资金原路返回及资源补偿仍由BE-012承担。

## 事务接线细化

1. 新增切换回执表与经济段表；回执与变更、凭据、方向唯一关联，经济段与期限修订唯一关联。两者保存原始JSON及哈希，身份和快照不可变，随资源变更事务一起提交或回滚。Redis成功而数据库回滚后，只能按原描述重放并核对，不得重新取切换时间或额度。
2. 有限额API以Stream ID作为切换水位。相同毫秒下须按序号数值比较，不能使用字符串顺序，也不能仅用请求预取的时间。水位前的逐次事实须与切换回执中的已用量相符，水位后的事实才计入新段；同时核对数据库追平、来源连续性及Redis月桶计数。
3. 资金来源由服务端沿订单、订阅、已完成升级、资金关联及实际支付记录确定。范围为同一企业、产品、订阅组合和代次内的期限原支付及已完成升级补款；不得跨组合或代次借用。申请阶段按最近补款优先预留，审批时复核同一经济段及资金分配并冻结；其间不重新分配已预留资金，不因客户端提交支付ID而改变分配顺序。一个组合包含当前和未来续费订单时，不能只允许退款单使用自身原支付，却允许其先占完共享升级款，导致另一期有经济可退余额但无法使用组合内剩余现金。
4. 资金分配表关联退款单、支付来源、来源订单、经济段及其哈希。锁顺序为当前订单、企业/订阅组合、按ID排序的支付来源；不再锁其他来源订单。拒绝后按退款状态释放占用，已完成/执行中占用继续保留。已有分配的退款不得再按兼容性payment_id将整笔金额重复扣到单一来源。
5. 版本变更与普通退款共用订阅组合的互斥边界；普通退款在途时不得启动新版本变更，版本变更在途时不得冻结普通退款。降级与补偿也必须计入普通退款对同一支付来源的占用。
6. 审批保存经济段计划和资金腿、审计及通知发件箱，任一失败全部回滚。审批通过不等于退款执行完成；BE-012仍须在资金与资源操作前复核实际用量及恢复条件，不能直接执行过期报价。

API可信切换路径优先接入。不能从SaaS状态查询的本地观察时间反推第三方真实生效时间；缺少可验证生效证据的历史SaaS修订仍标记人工核定，不以新接口存在冒充已完成联调。

### 本轮验证矩阵

| 范围 | 必须验证的条件 |
| --- | --- |
| 回执持久化 | Redis原回执一致、target读回一致、来源epoch与注册时间可信、事务回滚、重复写入幂等、快照不可修改 |
| 经济段生成 | 最新修订及目标账本对应、当前与未来期限独立、未完成/补偿不可信、缺最新窗口不回退旧窗口 |
| 水位计量 | 相同毫秒序号数值比较、切换前后归属、预取时间早于切换的后扣额仍计入新段、PG追平及月桶勾稽、过期窗口不能漏掉原月份 |
| 多来源预留 | 最近补款优先、同组合多期现金余额共用但额度不叠加、跨订单共享来源不超退、跨企业/币种/代次拒绝、拒绝释放、已完成退款及在途金额只扣一次 |
| 审批冻结 | 原资金分配与经济段哈希复核、并发审批版本控制、审计或消息发件箱失败全回滚、成本不向买方暴露 |
| 集成边界 | 普通退款与版本变更互斥、降级/补偿尊重普通退款占用、真实PG行锁验证、无真实资金执行及无业务订单清理 |
