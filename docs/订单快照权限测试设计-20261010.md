## 首轮风险与修复复测

以下三项为加固前的历史发现，已在最新源码上复测关闭。交付任务配置、订单文件列表和下载入口现在调用严格的 `delivery_snapshot`；`order_cost` 与清算比例读取调用严格的 `economic_snapshot`。源码检查确认新增金额/成本列一致性、月数与有限合法比例校验；本轮 16 项实测确认原有缺失字段、缺失方式、缺失上限样例均拒绝处理，没有为新增校验的每一种非法值增加穷举用例。

### P1：交付上限缺失被解释为不限次

旧版定位：`backend/app/main.py:6741` 的订单文件列表与 `:6699` 的下载入口使用 `json.loads(...).get("download_limit", 0)`。

HTTP 实测原本限次 2 的新订单，在交付快照变成 `{}` 或仅删除 `download_limit` 后，文件列表返回 200 和 `download_limit: 0`。源码中下载入口仅在上限大于 0 时限制次数，因此缺失配置可以绕过限次，未满足 fail-closed。本测试实际验证的是文件列表响应；真实文件下载未执行，下载入口行为来自代码检查。

建议主 agent 对 snapshot_version=1 的交付快照做必填字段/类型校验；区分明确配置的 0 与缺失字段，缺失返回 409，两个入口共享校验。

### P1：缺失交付方式仍确认支付并生成错误任务

旧版定位：`backend/app/main.py:1876` 的 `delivery_task_config` 与 `create_delivery_task`。

新订单 `delivery_method_snapshot` 置空后，HTTP 支付确认仍返回 200，`payment_status=paid`、`delivery_status=preparing`、公开交付方式为空。源码将未知/空方式落入 manual 分支，缺失快照没有阻断资金状态和任务生成。

建议主 agent 在支付业务写入前校验交付快照方式及必要配置，缺失/未知方式返回 409，保留订单和支付的 unpaid 状态。

### P1：经济快照必要金额/成本字段缺失仍允许清算

旧版定位：`backend/app/order_economics.py:117` 的 `economic_snapshot`、`backend/app/main.py:1775` 的 `order_cost` 和 `:5353` 的清算分支。

经济快照校验仅检查 schema_version 和规则版本/比例键。分别删除 JSON 中 `amount`、`unit_cost` 或 `total_cost` 后，三个独立订单的首次 HTTP 清算均返回 200，并生成清算单，结果仍取 Order 的金额与独立总成本列。虽然本次未出现金额算错，完整经济快照缺失没有触发拒绝，削弱审计和数据一致性保障。

建议主 agent 校验 schema_version=1 的完整经济字段及类型，并校验 JSON 与独立金额/成本列的一致性，拒绝缺失或冲突数据，不回退到当前版本价格/成本。
